## L2: 数据范围审查

### 发现 1: `clean_orphan_edges` 空集合语义不一致 — HIGH

**位置**: `core/graph.py:548` vs `memory/curator.py:930`

`GraphIndex.clean_orphan_edges(valid_ids)`:
```python
if not valid_ids:
    # Empty set means all rows are orphaned
    deleted += conn.execute("DELETE FROM edges").rowcount
    deleted += conn.execute("DELETE FROM graph_meta").rowcount
```

`curator.clean_orphan_edges(mem_store)`:
```python
all_ids = {m.id() for m in mem_store.list_active()}
if not all_ids:
    return 0  # <-- 空集合时直接跳过，不调用 graph 清理
return gm.store.clean_orphan_edges(all_ids)
```

**矛盾**: GraphIndex 层将空 valid_ids 视为"全部清理"，但 curator 层在空集合时直接返回 0，**完全跳过了清理**。当 mem_store 中没有 active memories（如全新实例、所有记忆已被归档）时，graph 中残留的旧 edges/meta 不会被清理。

**影响**: 在 edge case 场景下（空 store + 非空 graph），orphan edge cleanup 漏执行。

### 发现 2: `MemoryFrontmatter.to_dict()` 默认值省略导致 `rank=0` 丢失 — MEDIUM

**位置**: `core/store.py:588-597`

```python
def to_dict(self) -> Dict[str, Any]:
    d: Dict[str, Any] = {}
    for f in ("id", "created", ..., "rank", "version"):
        v = getattr(self, f)
        if v is not None and v != [] and v is not False and v != 0 and v != "general" and v != "medium":
            d[f] = v
        elif f in ("id", "created", "source", "confidence"):
            d[f] = v
```

`rank` 的默认值是 0，但省略条件 `v != 0` 意味着 `rank=0` 永远不会被序列化。`version` 同理（默认 1，不会被省略）。

**影响**: 
- 读取 frontmatter YAML → `from_dict()` → 修改 → `to_dict()` → 写入时，`rank=0` 丢失
- 但由于 `from_dict()` 使用 `cls(**filtered)` 且 dataclass 有默认值，反序列化后 `rank` 会恢复为 0
- **实际影响有限**：这是幂等的（round-trip 后 rank 仍为 0）

**判定**: 设计意图（省略默认值保持文件整洁），非缺陷。但值得记录。

### 发现 4: `list_active()` 在 curator 中可能遗漏 superseded memories — MEDIUM

**位置**: `memory/curator.py:929`

```python
all_ids = {m.id() for m in mem_store.list_active()}
```

`list_active()` 只返回非 superseded 的记忆。但 orphan edge cleanup 的目标是"删除指向不存在 memories 的边"。如果一个 memory 被 superseded 但仍有 edges 指向它，这些 edges 会被视为"orphan"并被清理——这是正确的。

但如果一个 memory **自身**是 superseded 但仍存在于 graph_meta 中，它的 edges 应该被清理吗？从语义上说，superseded memory 已被逻辑替换，其 graph 关联也应清理。`list_active()` 不包含 superseded memories，因此这些关联会被正确清理。

**但**: 如果 curator 的运行时序是 reflection → compaction → curator，而 compaction 可能将某些 memories 标记为 superseded，那么 curator 的 `list_active()` 将不再包含它们，orphan cleanup 会清理其 edges。这是正确的管道行为。

**判定**: 语义正确。`list_active()` 用于 orphan cleanup 是合适的。

## L3: 副作用顺序审查

### 发现 1: `merge_similar` 中 keeper 不记录 lineage — MEDIUM

**位置**: `memory/curator.py:876-898`

```python
# Update keeper
mem_store.update(keeper.id(), body=merged_body, tags=merged_tags)

# Archive the other via supersedes + cold storage
entry = {
    "id": archived.id(),
    ...
    "supersedes": [keeper.id()],  # Mark archived as superseded by keeper
}
if _append_to_cold_store(mem_store, entry):
    try:
        mem_store.delete(archived.scope, archived.id())
        merged += 1
    except Exception:
        pass
```

`merge_similar` 合并两个相似记忆时：
1. 更新 keeper 的 body 和 tags
2. 将 archived 写入 cold storage，并标记 `"supersedes": [keeper.id()]`
3. 从 active store 删除 archived

**问题**: keeper 本身**没有记录**它 superseded 了 archived。正常的 supersedes 语义是双向的（新版本标记旧版本为 superseded，旧版本标记新版本为 successor）。但这里只有 archived → keeper 的单向链接。

**影响**: 
- 如果 archived 因为 delete 失败仍留在 active store（`except Exception: pass`），搜索结果可能返回重复内容
- 没有完整的 lineage 链可供追溯合并历史
- 测试 `test_merge_similar_updates_keeper_body` 等未验证 keeper 的 supersedes 字段

**根因**: merge 逻辑将 archived 视为"被 keeper 取代"，但没有在 keeper 上建立反向链接。

## L4: 后效遗漏审查

L4 关注：缓存/索引/统计值是否在数据修改后同步更新？

### 审查方法

检查所有数据变更路径（put/update/delete/reorder/prune/curator archive）后：
1. `MemoryStore._mark_changed()` 是否被调用
2. `SearchIndex.invalidate_cache()` 的 4 层缓存是否被清理
3. `GraphIndex` 的 adjacency/PageRank 缓存是否需要失效
4. Entity index 和 aggregated stats 的一致性

### 发现 1: `prune_index()` 遗漏 `_mark_changed()` — MEDIUM

**位置**: `core/store.py:2280-2330`

```python
def prune_index(self) -> Dict[str, Any]:
    # ... 删除 stale rows, stats, entity_links ...
    conn.commit()
    return {"pruned": len(removed), "pruned_ids": removed}
```

`prune_index()` 删除 SQLite 中文件已不存在的 memories 及其关联的 stats/entity_links，但**没有调用 `_mark_changed()`**。

**影响**: 如果 `prune_index()` 在运行时（非初始化阶段）被调用，且 `SearchIndex` 的缓存仍有效，后续搜索可能返回已被 prune 的 "幽灵" memory。

**缓解**: `prune_index()` 当前主要在 `_sync_from_disk()`（初始化）时调用，初始化时 `_search_index` 为 `None`，所以实际影响较小。但 API 层面暴露了运行时调用风险。

**建议**: 在 `conn.commit()` 后添加 `self._mark_changed()`。

---

### 发现 2: `GraphIndex` 无 adjacency/PageRank 缓存 — 性能观察（非缺陷）

**位置**: `core/graph.py:306-353`

`pagerank()` 每次调用都重新从 SQLite 全表扫描构建 forward/reverse adjacency：
```python
rows = conn.execute("SELECT source_id, target_id, weight FROM edges").fetchall()
# Build adjacency from scratch every call
```

`spread()` 每次迭代都通过 `_neighbors_raw()` 实时查询 edges：
```python
for neighbor in self._neighbors_raw(nid):
```

**判定**: 这是设计选择而非 L4 缺陷。GraphIndex 不维护内存缓存，所有查询实时命中 SQLite。对于 edges 规模 <10k 的场景，全表扫描性能可接受。若未来规模扩大，可考虑 adjacency 缓存 + mtime-based 失效机制。

## L5: 错误沉默审查

L5 关注：broad `except Exception` 是否掩盖了真实失败？数据一致性是否受影响？

### 审查方法

全仓库 grep `except Exception` 和 `except:` 模式（~200+ 处），按风险分层检查：
1. **数据一致性风险**：异常吞没后，数据是否处于不一致状态？
2. **功能降级路径**：异常后是否有正确的 fallback + 日志记录？
3. **日志级别是否恰当**：静默失败 vs warning vs debug 的区分

### 发现 1: Curator archive 后 delete 失败导致 cold/active store 双份数据 — HIGH

**位置**: `memory/curator.py:451-459`, `574-576`, `690-694`, `850-852`, `894-898`

```python

if _append_to_cold_store(mem_store, entry):
    try:
        mem_store.delete(mem.scope, mid)
        archived += 1
    except Exception as e:
        logger.warning(
            "Failed to delete memory %s after archiving: %s. "
            "Cold storage entry preserved; memory may be re-archived on next run.",
            mid, e,
        )

# Phase 2a/3b (archive_superseded, merge_similar)
if _append_to_cold_store(mem_store, entry):
    try:
        mem_store.delete(mem.scope, mid)
        archived += 1
    except Exception:
        pass  # <-- 无日志！
```

**问题**: 
- Phase 2a (`archive_superseded`) 和 Phase 3b (`merge_similar`) 的 delete 失败使用 `pass`，**完全静默**
- Cold store 中已写入备份，但 active store 中 memory 仍然存在
- 下次 curator 运行时会再次扫描到该 memory，可能重复 archive（如果 archive 逻辑去重不够严格）

**影响**: 数据冗余 + 潜在的无限 archive 循环（如果 delete 持续失败）。

**根因**: 不同阶段的错误处理不一致——Phase 1 有 warning，Phase 2a/3b 完全静默。

**建议**: 统一使用 warning 级别日志，并考虑将"delete 失败"标记为 curator report 中的错误项。
