# v1.6 额外深度根因审查

**日期**: 2026-06-12  
**基于报告**: `docs/dev/1.6/v1.6-round2-code-review-report.md`  
**方法**: systematic-debugging 根因追踪 + 6-layer 历史缺陷矩阵 + 开发者视角架构复盘  
**审查目的**: 判断第二轮问题的真实根因是功能意图设计问题，还是程序框架与代码实现设计问题，并推导可能遗漏的问题与更有效的优化方案。

---

## 1. 核心判断

第二轮报告里的 4 个问题不是 4 个彼此独立的 bug。它们共享同一个更深层根因：

> v1.6 把 `user_id` / `agent_id` / `run_id` 定义成“运营级基础设施能力”，但实现时没有把它提升为一等领域概念，而是把它当成三个可选字符串字段在各入口手工透传。

因此，真实根因不是单纯的“某个函数忘了传 filters”。更准确的判断是：

| 层面 | 是否是根因 | 判断 |
|---|---|---|
| 功能意图设计 | 是，约占 40% | `NULL/public`、scope graph、dashboard scope、curator scope 的语义没有被冻结成统一规则 |
| 程序框架设计 | 是，约占 45% | 缺少中心化 `ScopeContext` / `ScopeFilter` / `ScopePolicy`，导致每个入口靠手工拼 dict |
| 末端代码实现 | 是，约占 15% | `MemoryCreate` 漏字段、cache key 折叠、graph stats 全局读取是表层症状 |

换句话说：**v1.6 的功能方向是对的，但当前实现缺少一条能承载该功能的横切抽象。**

## 2. 从已发现问题反推真实根因

### 2.1 R2-C1 的真实根因不是 cache key 写错，而是 scope 值域没有领域模型

第二轮报告发现：

- `MemoryFrontmatter.new()` 接受 `user_id=""`
- `to_dict()` 把 `""` 当作 `None` 省掉
- `_upsert_memory_row()` 把 `""` 原样写入 SQLite
- `_search_impl()` cache key 用 `str(v or "")` 把 `None` 和 `""` 折叠

表层修复可以是“改 cache key”。但开发者视角下，真正的问题是：

> 代码库没有定义“scope 值是否合法、如何归一、空值代表什么、public 如何参与过滤”。

同一个 scope 值在不同层含义不同：

| 层 | 当前行为 | 暗含语义 |
|---|---|---|
| `MemoryFrontmatter.new()` | 接受 `""` | 空字符串是合法值 |
| `to_dict()` | `"" -> None` 后省略 | 空字符串不是合法业务值 |
| SQLite 写入 | 原样写 `""` | 空字符串是一个独立 tenant |
| `filters={"user_id": None}` | SQL `IS NULL` | `None` 是显式 public 查询 |
| cache key | `None` 与 `""` 相同 | 二者等价 |

这不是实现偶然失误，而是缺少领域不变量。

### 2.2 R2-H1 的真实根因不是 dashboard 漏字段，而是 tool 与 dashboard 没有共享 API contract

`runtime/schemas.py` 已经声明 `srh_memory_write` 支持 `user_id` / `agent_id` / `run_id`。  
但 `web/api.py::MemoryCreate` 没有这些字段，`create_memory()` 调 `_tool_srh_memory_write()` 时也没有透传。

根因不是开发者忘记加三行字段，而是：

> dashboard API 与 tool schema 是两套并行契约，没有共享请求模型、schema 片段或契约测试。

于是每次工具面新增参数，都必须记得同步：

- tool schema
- tool handler
- dashboard Pydantic model
- dashboard handler
- docs/DASHBOARD
- dashboard tests

这就是典型的 L1 contract drift 温床。

### 2.3 R2-H2 的真实根因不是 stats 写错，而是 graph 的 scope 语义没有设计

第二轮报告指出：

- `/stats?user_id=u1` 的 memory count 是 scoped
- 但 graph stats 来自 `gm.store.stats()`，是全局图
- `/graph?user_id=u1` 的 nodes 是 scoped
- 但 pagerank 来自 `gm.pagerank()`，仍是全局图中心性

这里有一个功能意图层缺口：

> v1.6 设计了 memory scope，但没有设计 graph scope。

`GraphIndex` 当前是 Hebbian co-activation graph，本质上是“记忆被共同使用”的全局关系。引入 tenancy scope 后，至少需要回答：

1. 跨 scope 的记忆能不能存在边？
2. 如果边存在，scoped 查询是否能看到边权影响？
3. scoped pagerank 是全图 pagerank 后取子集，还是先裁剪子图再重算？
4. public memory 与 scoped memory 之间是否允许关联？
5. graph stats 在 scoped dashboard 中应表示全局图健康，还是当前 scope 子图？

这些不是代码实现自然能推断出来的规则，必须由设计层定。

### 2.4 R2-M1 的真实根因是 mutation side-effect 没有统一上下文

dashboard create 后自动做 tag overlap graph association：

```python
all_mems = _get_store().list_active()
related = [...]
gm.associator.on_memory_coactivation([new_mem.id()] + related)
```

这个问题跟第二轮的 graph stats 问题同源：

> 写入动作的副作用没有接收同一个 scope context。

`srh_memory_write` 的主写入路径已经知道 `user_id` / `agent_id` / `run_id`，但 dashboard 在 handler 层另起一段 side-effect 逻辑，重新从全局 store 查询相关记忆。  
这说明当前框架没有一个“写入后副作用管线”，导致：

- conflict check 在 tool 中做
- graph association 在 dashboard 中做
- bridge mirror 在 tool 中做
- curator 在独立 action 中做
- entity refresh 在 store 中做

这些副作用各自选择是否携带 scope，上下文自然会漏。

## 3. 功能意图设计问题

### 3.1 `NULL = public` 的语义前后冲突

v1.6 SDD 写道：

- `NULL 字段匹配所有（向后兼容）`
- `记忆无此字段时对所有请求可见（NULL = public）`

但当前实现和测试实际采用的是：

- `filters={"user_id": "u1"}` 不包含 `user_id IS NULL`
- `filters={"user_id": None}` 显式查询 `IS NULL`
- `test_null_scope_excluded_by_specific_filter` 明确断言 scoped search 排除 NULL memory

这不是小差异。它决定了 public memory 是否会被 scoped 用户看到。

需要做产品级决策：

| 方案 | 语义 | 优点 | 风险 |
|---|---|---|---|
| A. `NULL = public and visible to all scoped queries` | `user_id=u1` 包含 `user_id IS NULL OR user_id='u1'` | 与 SDD 原文一致，向后兼容更强 | hosted multi-tenant 下 public 记忆可能泄漏 |
| B. `NULL = global-only / unscoped` | `user_id=u1` 只匹配 `user_id='u1'` | 隔离更强，当前测试接近此语义 | 与 SDD 和部分 docs 冲突 |
| C. 显式策略参数 | `visibility=public/private` 或 `include_public=true` | 语义最清晰 | 改动较大 |

开发者建议：如果目标包含 hosted / multi-tenant，优先选 B 或 C，不要把 `NULL` 自动视作所有 tenant 可见。

### 3.2 dashboard scope 是完整管理面，还是只读观察面

当前文档说 `/memories`, `/graph`, `/stats` 可按 scope 过滤，但 `/memories POST` 不支持 scope。  
这说明 dashboard 的功能意图没有定清楚：

- 如果 dashboard 是完整 memory manager，就必须支持 scoped create / update / delete / graph side-effect。
- 如果 dashboard 只是全局管理员视图，就不应该宣传它是 scoped management surface。

建议：v1.6 先将 dashboard 定义为“scope-aware admin surface”，即：

- list/search/graph/stats 支持 scope query
- create 支持写入 scope
- update 不允许修改 scope
- delete 可以按 id 删除，但 UI 应显示 scope，避免误删

### 3.3 graph 与 scope 的关系缺少设计

Memory scope 是隔离维度；Graph 是关联维度。两者叠加后不能靠 `list_active(filters=...)` 自动解决。

建议为 v1.6.1 增补 graph scope policy：

```text
Graph edge creation:
- private-private: only same normalized scope may associate
- public-private: allowed only if policy include_public_edges=true
- public-public: allowed

Graph read:
- scoped graph view returns induced subgraph over visible memory IDs
- pagerank for scoped view is recomputed or explicitly marked global_pagerank
- stats returns both graph_global and graph_visible when needed
```

## 4. 程序框架与代码实现设计问题

### 4.1 缺少中心化 `ScopeContext`

当前 scope 在代码里表现为裸 dict：

```python
{"user_id": user_id, "agent_id": agent_id, "run_id": run_id}
```

裸 dict 的问题：

- 无归一入口
- 无空字符串规则
- 无 unknown key 策略
- 无 cache key 策略
- 无 SQL clause 策略
- 无“是否包含 public”策略
- 无 response serialization 策略

建议新增一个非常小的领域模型，避免过度设计：

```python
@dataclass(frozen=True)
class ScopeContext:
    user_id: str | None = None
    agent_id: str | None = None
    run_id: str | None = None

    @classmethod
    def from_mapping(cls, data: Mapping[str, Any] | None) -> "ScopeContext": ...
    def to_filter_dict(self) -> dict[str, str | None]: ...
    def cache_key(self) -> tuple[tuple[str, str, str], ...]: ...
    def matches(self, fm: MemoryFrontmatter, *, include_public: bool = False) -> bool: ...
```

这里最重要的不是类本身，而是把 scope 的不变量集中到一个位置。

### 4.2 缺少中心化 scope SQL builder 和 in-memory matcher 的同源性

当前已有 `_build_scope_clauses()`，但 in-memory 过滤仍散落在：

- `core/search.py::check_conflict`
- `tests/_helpers.py::MockStore.list`
- `web/api.py`
- curator scope grouping

建议把 SQL builder 和 Python matcher 都挂到同一 scope 模块：

- `normalize_scope_value()`
- `normalize_scope_filters()`
- `scope_cache_key()`
- `build_scope_sql_clauses()`
- `memory_matches_scope()`
- `scope_key_for_memory()`

这样可以避免 SQL 路径和 Python 路径语义分叉。

### 4.3 缺少“入口面同步”的契约测试

当前已经有 schema module tests，但它们主要验证 schema 存在和 register 使用 schema。  
缺少的是“同一能力在 tool 和 dashboard 两个入口都存在”的 contract tests。

建议增加能力矩阵测试：

| 能力 | Tool | Dashboard | Store/Search | Test |
|---|---|---|---|---|
| scoped write | `srh_memory_write` | `POST /memories` | `MemoryFrontmatter.new` + `put` | 同一字段落库 |
| scoped search | `srh_memory_search` | `GET /memories?user_id=` | `SearchIndex.search` | 同一结果集合 |
| scoped stats | N/A | `GET /stats?user_id=` | `list_active(filters)` + graph visible stats | 同域统计 |
| scoped graph | graph tools or dashboard | `GET /graph?user_id=` | graph induced subgraph | 不泄漏节点/边/score |

### 4.4 graph side-effect 没有统一 mutation pipeline

当前副作用散落，建议抽出最小的 mutation context，而不是新建大型框架：

```python
@dataclass(frozen=True)
class MemoryMutationContext:
    scope: str
    scope_context: ScopeContext
    source: str
    actor_id: str = "agent"
    session_id: str = ""
```

写入路径返回 `LoadedMemory` 后，统一调用：

- event ledger
- entity refresh
- conflict metadata
- graph association
- bridge mirror

短期不必全量重构，但 dashboard 不应自己做全局 graph association。

## 5. 已验证的遗漏风险全景

本轮对第二轮报告未直接列出的入口做了额外验证。结论是：底层 `MemoryStore.list_active(filters=...)` 与 `_build_scope_clauses()` 已具备部分能力，但多个上层入口仍未统一消费 scope context。也就是说，遗漏不是孤立漏参，而是同一根因在 palace、profile、context、curator、dashboard query、test double、schema contract 上的投影。

验证命令：

- `pytest tests/test_palace_recall.py tests/test_context.py tests/test_runtime_import_hygiene.py tests/test_schema_module.py -q`：`51 passed`
- `pytest tests/test_scope_filters.py -q`：`22 passed`
- `python -c "...MockStore..."`：确认 `MockStore.list_active(filters=...)` 抛出 `TypeError`
- `python -c "...runtime/schemas.py..."`：确认 search/delete schema 接受未知 filter key

### 5.1 已确认：`srh_palace_recall` / `srh_palace_search` 绕过 scope filters

证据：

- `runtime/tools.py:543-555`：`srh_palace_recall` 只读取 `topic`、`limit`、`zone`，调用 `mem_store.search(..., zone=zone)` 或 `mem_store.search(...)`，没有 `filters` 参数。
- `runtime/tools.py:589-602`：`srh_palace_search` 只读取 `query`、`limit`，调用 `mem_store.fusion_search(query, k=k * 2)`，没有 `filters` 参数。
- `tests/test_palace_recall.py:1-7` 明确是 zone filter-after-truncate 的回归测试；`rg` 未发现 palace 工具的 `user_id` / `agent_id` / `run_id` 测试。
- 定向测试 `tests/test_palace_recall.py` 通过，说明现有测试不能证明 palace scope isolation。

根因归类：程序框架 / 代码实现设计问题为主。`srh_memory_search` 已有 `filters` 路径，但 palace 工具没有复用统一 scope filter contract。

风险：hosted / multi-agent 场景下，agent 可通过 palace recall/search 看到同 zone/topic 下其他 scope 的记忆。

建议：要么把 palace 工具明确标注为 global/admin-only tool，并在注册或调用层限制；要么补 `filters` 参数并复用同一个 `ScopeContext` / `normalize_scope_filters()`。

### 5.2 已确认：profile / palace compilation 使用全局 active memories

证据：

- `runtime/tools.py:705-722`：`_compile_profile_via_llm()` 使用 `mem_store.list_active()`；zone 模式再调用 `mem_store.group_by_zone()`。
- `core/store.py:952-955`：`group_by_zone()` 内部固定遍历 `self.list_active()`，没有 filters。
- `tests/test_runtime_import_hygiene.py:95-140` 只验证 compile profile 的运行绑定与写出路径，fake store 的 `list_active()` 也不支持 scope。
- 定向测试 `tests/test_runtime_import_hygiene.py` 通过，但没有覆盖多 user / agent / run 的编译隔离。

根因归类：功能意图设计问题和实现设计问题各占一半。代码把 profile/palace compilation 当作本地单用户汇总能力；v1.6 没有重新定义 hosted scope 下的 profile 语义。

风险：一个 store 内有多个 user 时，`profile.md`、`palace-index.md`、zone summary 可能混合多个用户或 agent 的长期记忆，后续再被 context 或工具读取时形成二次泄漏。

建议：先做产品语义决策：profile 是 per-scope artifact，还是 local-only global artifact。若选择 per-scope，则 compile schema、handler、输出路径和 cache key 都必须带 scope。

### 5.3 已确认：context injection 仍是无 scope 召回

证据：

- `memory/context.py:149-168`：pinned 使用 `store.list_pinned()`，dynamic recall 使用 `search.search(query, k=10)`，fallback 使用 `store.list_active()[:10]`，均无 scope 参数。
- `memory/context.py:227-230`：`build_context()` 没有 scope 参数，只转调 `build_context_bundle(...)`。
- `tests/test_context.py:97-489` 覆盖优先级、stable/dynamic 分离、压缩、空输入等行为，但未出现 `user_id` / `agent_id` / `run_id` 断言。
- 定向测试 `tests/test_context.py` 通过，说明 context 的旧行为稳定，但不能证明 v1.6 isolation。

根因归类：程序框架 / 代码实现设计问题为主。context builder 是最需要消费 session/user scope 的入口之一，但接口仍停留在 v1.4 的全局 store/search 形态。

风险：这是比 dashboard 更高优先级的泄漏面。即使显式 `srh_memory_search(filters=...)` 正确，LLM prompt 注入仍可能从全局 search/list_active 取到其他 scope 的记忆。

建议：给 `build_context_bundle()` / `build_context()` 增加 `scope_context` 或 `filters`，并要求 runtime hook/session 层传入；`list_pinned()`、episode summary、fallback path 也要做相同 scope 策略。

### 5.4 已确认：curator 只有 `MergeSimilar` 部分 scope-aware

证据：

- `memory/curator/actions.py:124`：`ArchiveStale` 从 `mem_store.list_active()` 全局扫描。
- `memory/curator/actions.py:196`：`CompactChains` 从 `mem_store.list_active()` 全局扫描。
- `memory/curator/actions.py:391-409`：`MergeSimilar` 先全局 `list_active()`，再按 `(user_id, agent_id, run_id)` 分组。
- `memory/curator/actions.py:436-442`：`MergeSimilar` 只在 scope group 内扫描 pair，这是 v1.6 已补的一部分。
- `memory/curator/actions.py:567-568`：`CleanOrphanEdges` 用全局 active ids 清 orphan edges。
- `tests/test_curator_pipeline.py` 大量覆盖 action 行为，但检索未发现 curator 对 `user_id` / `agent_id` / `run_id` 的隔离测试。

根因归类：功能意图设计问题为主。curator 到底是 admin global maintenance，还是 tenant-scoped maintenance，没有被冻结；实现只能出现“部分 action 修了、部分 action 仍全局”的状态。

风险：如果 curator 在 hosted mode 自动运行，Archive/Compact/Clean 可能跨 scope 影响记忆生命周期或图边清理。若它是 admin-only 全局维护，当前实现可以成立，但必须在 policy 和入口权限上写清楚。

建议：定义 curator policy：

- local single-user：允许 global curator
- hosted user/session：默认 per-scope curator
- admin maintenance：允许 global curator，但必须显式 admin mode，并在报告/日志中标注 scope

### 5.5 新增确认：dashboard `/query` cross-layer endpoint 也是 scope-unaware

证据：

- `web/api.py:161-172`：`_CrossLayerQueryCompat.query()` 参数没有 `user_id` / `agent_id` / `run_id` / `filters`，调用 `self.store.search(..., zone=zone, include_history=...)`。
- `web/api.py:185-188`：PageRank 取 `self.gm.pagerank()` 全局分数。
- `web/api.py:841-852`：`GET /query` 只接受 `q`、`zone`、`k`，无法传 scope。
- `tests/test_dashboard.py:77` 只检查 dashboard HTML 有 `graph`、`query` 等 tab 文本；未覆盖 `/query` scope behavior。

根因归类：程序框架 / 代码实现设计问题为主。dashboard 的 `/memories`、`/graph`、`/stats` 开始各自补 scope 参数，但 `/query` 仍走旧 cross-layer compat adapter。

风险：即使 `/memories?user_id=...` 已隔离，用户仍可通过 `/query?q=...` 走 unscoped search + global pagerank 得到跨 scope 结果。

建议：把 `/query` 纳入同一 dashboard scope policy；若继续支持 cross-layer score，graph score 必须来自 scoped induced subgraph，而不是 global pagerank。

### 5.6 已确认：`MockStore.list_active()` 与真实 store 签名不一致

证据：

- `core/store.py:940-941`：真实 store 是 `list_active(self, filters: Optional[Dict[str, Optional[str]]] = None)`。
- `tests/_helpers.py:159-160`：`MockStore.list_active(self)` 无 filters。
- `tests/_helpers.py:172-179`：`MockStore.list(..., filters=None)` 本身有 filter 逻辑。
- 动态探针输出：`MockStore.list_active() got an unexpected keyword argument 'filters'`。

根因归类：测试基础设施设计问题。mock 已经具备 `list(filters=...)`，但常用便捷方法没有同步真实签名，导致新增 scope 透传的测试要么写不出来，要么绕过生产同款调用路径。

风险：上层代码如果开始正确调用 `list_active(filters=...)`，部分 mock 测试会因为签名不一致失败；反过来，现有 mock 也无法帮忙发现“忘记传 filters”的真实问题。

建议：立即让 helper mock 对齐 production：

```python
def list_active(self, filters=None):
    return self.list(active_only=True, filters=filters)
```

同时把 curator/context/dashboard 的新 scope 测试都落到这个 shared helper 上，避免每个测试文件自造不同语义的 fake store。

### 5.7 已确认：schema 对 scope filters 的结构约束不足

证据：

- `runtime/schemas.py:26-37`：`_SRH_MEMORY_SEARCH_SCHEMA.properties.filters` 只是 `"type": "object"`。
- `runtime/schemas.py:39-51`：`_SRH_MEMORY_DELETE_SCHEMA.properties.filters` 同样只是 `"type": "object"`。
- `tests/test_schema_module.py:85-94` 只验证 delete schema 接受 `{filters: {}}` 且拒绝 `{}`，未验证 unknown filter key。
- 动态探针确认 `{"filters": {"bad": "v"}}` 同时被 search/delete schema 接受。
- `core/store.py:967-970` 会在 store 层拒绝 unknown keys；问题不在最终 SQL 层，而在 host/tool schema 层不能提前拒绝 typo。

根因归类：接口契约设计问题。v1.6 把 scope filter 作为自由 object 暴露给 host，但真正允许的 key 只有三个。

风险：调用方 typo 会通过 schema 校验，直到 runtime/store 层才报错；如果某些入口没走 store 的 `_build_scope_clauses()`，还可能静默退化为 unscoped 行为。

建议：抽共享 schema 片段：

```json
{
  "type": "object",
  "properties": {
    "user_id": {"type": ["string", "null"]},
    "agent_id": {"type": ["string", "null"]},
    "run_id": {"type": ["string", "null"]}
  },
  "additionalProperties": false
}
```

并同步到 search/delete/tool docs/schema tests。

## 7. 开发者视角最终判断

### 最根本原因

最根本原因是：**v1.6 引入的是横切型运行时能力，但代码按局部字段扩展来实现。**

这导致：

- 值域规则分散
- 入口契约分散
- 副作用上下文分散
- graph 与 memory 的作用域语义分散
- docs、tests、schema、dashboard 各自维护一份“近似理解”

### 不是主要根因的点

以下都只是症状：

- cache key 写法不够严谨
- dashboard 漏了三个字段
- graph stats 用了全局 stats
- auto-associate 用了全局 list

它们需要修，但只修这些点，后续 palace、profile、context、curator 仍会继续出现同类漏传。

### 最有效的优化方向

最高收益的优化不是大规模重构，而是建立一个很小但强约束的 scope 层：

```text
ScopeContext + ScopePolicy + shared matcher/sql/cache/schema helpers
```

这会把当前的“靠开发者记忆透传三字段”变成“入口必须先构造 scope，上下游只能消费规范化 scope”。

从成本收益看，这是 v1.6 后续最值得优先做的结构性修复。
