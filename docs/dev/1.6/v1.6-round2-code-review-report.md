## 1. 审查结论

本轮复审确认：v1.6 第一轮修复的主干问题大多已经落地，`schema drift`、`scope filter` 主路径、`history` 反序列化、`graph expansion` 越权提示等问题已基本收口。  
但当前最新代码里仍残留 **3 个高风险功能缺陷 + 1 个中风险架构回退点**，其中最严重的问题已经形成了**可复现的 scope 语义污染与搜索缓存串扰**。

| 严重级别 | 数量 | 结论 |
|---|---:|---|
| CRITICAL | 1 | 必须优先修复，当前会返回错误的 scoped search 结果 |

## 2. 分阶段审查

### Phase 1: Root Cause Investigation

- 对照 `docs/design/1.6/v1.6-sdd.md` 与现有 `docs/dev/1.6/v1.6-code-review-report.md`，确认 v1.6 的真实目标仍然是两条主线：
  - `Memory Event Ledger`
  - `Scoped Filters (user_id / agent_id / run_id)`
- 从最新代码逆向检查 v1.6 的真实落点：
  - 数据模型入口：`core/models.py`
  - 持久化入口：`core/store.py`
  - 检索与缓存：`core/search.py`
  - tool surface：`runtime/tools.py` + `runtime/registration.py`
  - dashboard surface：`web/api.py`
- 针对历史高频缺陷层优先检查：
  - L5 `Error silence / silent degradation`
  - L3 `Side-effect order / context propagation`
  - L1 `Interface contract / schema drift`
  - L2 `Scope semantics / mock divergence`

### Phase 2: Pattern Analysis

本轮发现的问题，与该仓库既往审查中高频模式高度一致：

- **L2 + L5 复合模式**: scope 值没有在所有层统一归一，导致“公开可见(None)”与“空字符串 scope”并存。
- **L1 模式**: dashboard 的读接口已升级为 v1.6 scope-aware，但写接口仍停留在 pre-v1.6 契约。
- **L3 模式**: dashboard 写入后的 graph auto-associate 仍按全局 active 集合执行，没有继承 scope 上下文。
- **L4 模式**: `/stats` 的 memory 统计已 scoped，但 graph 统计仍是全局值，形成双来源聚合不一致。

### Phase 3: Hypothesis and Validation

实际验证：

1. 运行定向测试：
   - `pytest tests/test_scope_filters.py tests/test_schema_module.py tests/test_dashboard.py -q`
   - 结果：`55 passed, 1 failed`
2. 失败项不是本轮发现的主缺陷，而是现有 dashboard 测试把 curator 报告写到 `C:\Users\Huang\.hermes\memory\cold_store.report.json`，在当前受限环境下触发 `PermissionError`。
3. 对 scope 空字符串问题做了最小复现：
   - `MemoryFrontmatter.new(source='test', user_id='')` 生成的对象会保留 `user_id == ''`
   - `to_dict()` 会把该字段省掉，表现为 frontmatter 侧视作 `None`
   - `_upsert_memory_row()` 会把 `''` 原样写入 SQLite
   - `SearchIndex._search_impl()` 的 cache key 会把 `None` 和 `''` 都折叠成同一个 `""`
4. 最小复现输出表明：
   - 第一次 `filters={'user_id': None}` 返回空
   - 第二次 `filters={'user_id': ''}` 返回命中
   - 第三次再次查询 `filters={'user_id': None}`，由于缓存键冲突，错误返回了第二次的结果

### Phase 4: Review Judgment

结论不是“局部代码风格欠佳”，而是 **v1.6 的 scope 契约在 dashboard surface 与 cache layer 上仍然存在未闭合边界**。  
尤其是第一个问题，已经从“语义不一致”升级成“错误结果可复现”。

## 3. 分层级发现

### Finding R2-C1 [CRITICAL] scope 空字符串与 `None` 未统一，导致 scoped search 缓存串扰并返回错误结果

**层级归类**: L2 `Data scope semantics` + L5 `Silent degradation`  
**位置**:

- `core/models.py:50-73`
- `core/models.py:87-90`
- `core/store.py:514-544`
- `core/search.py:591-603`

**问题**:

- `MemoryFrontmatter.new()` 接受 `user_id=""` / `agent_id=""` / `run_id=""`
- `to_dict()` 会把空字符串 scope 当成 `None` 清掉
- 但 `_upsert_memory_row()` 会把空字符串原样写进 SQLite
- `_search_impl()` 生成缓存键时使用：

```python
filter_tuple = tuple(sorted((str(k), str(v or "")) for k, v in (filters or {}).items()))
```

这会把：

- `{"user_id": None}`
- `{"user_id": ""}`

折叠成同一个 cache key。

**影响**:

- scope 语义出现“双重真相”：
  - frontmatter / 文档层看起来像 public
  - SQLite / 查询层却把它当成独立的空字符串租户
- 更严重的是，缓存会让一次 `user_id=""` 的查询污染 `user_id=None` 的结果，直接返回错误的 scoped search 响应。

**复现结论**:

- 第一次查 `filters={"user_id": None}`: `[]`
- 第二次查 `filters={"user_id": ""}`: `[<memory_id>]`
- 第三次再查 `filters={"user_id": None}`: 错误返回 `[<memory_id>]`

**建议修复**:

1. 在进入所有 v1.6 scope 通道前统一归一：`"" -> None`
2. `MemoryFrontmatter.new()`、tool handler、dashboard handler、`_build_scope_clauses()` 使用同一归一逻辑
3. `SearchIndex._search_impl()` 的 cache key 必须保留 `None` 与 `""` 的语义差异，或更彻底地禁止空字符串进入 scope 过滤面

### Finding R2-H1 [HIGH] dashboard 写接口未暴露 v1.6 scope 字段，读写契约断裂

**层级归类**: L1 `Interface contract drift`  
**位置**:

- `web/api.py:53-60`
- `web/api.py:281-289`

**问题**:

- `MemoryCreate` 只允许：
  - `body`
  - `zone`
  - `confidence`
  - `tags`
  - `pinned`
  - `scope`
- 没有 `user_id` / `agent_id` / `run_id`
- 但同文件的 `/memories`, `/graph`, `/stats` 已经接受 v1.6 的 scope filter 参数

这意味着 dashboard surface 目前是：

- **读路径**: v1.6 scope-aware
- **写路径**: 仍是 pre-v1.6

**影响**:

- 通过 dashboard 创建的记忆无法写入 scoped metadata
- dashboard 管理端无法完整演练 v1.6 的多用户 / 多 agent / 多 run 场景
- 接口层与 `runtime/tools.py::_tool_srh_memory_write()` 的真实能力不一致

**建议修复**:

1. 在 `MemoryCreate` 中补齐三元 scope 字段
2. `create_memory()` 调用 `_tool_srh_memory_write()` 时透传这些字段
3. 为 dashboard 增加 scoped create 的集成测试

---

### Finding R2-H2 [HIGH] dashboard 的 scoped `/stats` 和 `/graph` 仍混入全局 graph 指标，破坏作用域隔离语义

**层级归类**: L4 `Aggregation inconsistency` + L3 `Context propagation`  
**位置**:

- `web/api.py:398-454`
- `web/api.py:687-695`
- `runtime/graph.py:306-313`
- `runtime/graph.py:407-427`

**问题**:

- `/graph` 节点列表来自 `list_active(filters=...)`
- 但 `pagerank_scores = gm.pagerank()` 是全图全局值
- `/stats` 的 `memory_count` 与 `zones` 基于 scoped `memories`
- 但 `graph_stats = {**gm.store.stats()}` 是全局图统计

**影响**:

- `GET /stats?user_id=u1` 返回的 memory 统计与 graph 统计不再属于同一作用域
- `GET /graph?user_id=u1` 返回的节点虽然被过滤，但其 pagerank 仍然受其他 scope 的隐藏节点影响
- 这违反了 `docs/DASHBOARD.md` 对 scoped graph/stats 的语义承诺

**建议修复**:

1. 明确决定 dashboard 的 graph scope 语义：
   - 方案 A: 明确标注“节点过滤，图指标全局”
   - 方案 B: 对 scoped 子图重新计算 pagerank / node_count / edge_count
2. 若选择 B，`/stats` 不能再直接透传 `gm.store.stats()`
3. 为 `/graph` 与 `/stats` 增加 scoped integration tests，校验 graph 指标与 memory_count 同域

---

### Finding R2-M1 [MEDIUM] dashboard 创建后 graph auto-associate 仍按全局 active 集合关联，后续扩展 scope 写入时会重新引入跨 scope 图污染

**层级归类**: L3 `Context propagation leak`  
**位置**:

- `web/api.py:300-315`

**问题**:

创建记忆后，dashboard 直接做：

```python
all_mems = _get_store().list_active()
related = [m.id() for m in all_mems if ... tag overlap ...]
```

这里没有继承任何 scope 上下文。

**当前状态**:

- 由于 `MemoryCreate` 还没暴露 scope 字段，这个问题暂时被“H1 的接口缺口”部分掩盖
- 但一旦 dashboard 写入补齐 scope，该逻辑会立刻退化成跨 scope 自动连边

**建议修复**:

1. 在 dashboard create 补 scope 字段时，同步把 auto-associate 限制到同 scope active 集合
2. 若 scope 为空，则明确将其视为 public，而不是回退到“全局无边界”

## 6. 最终判断

v1.6 的核心实现已经比首轮审查时稳定很多，但从 `systematic-debugging` 的经验看，这一版现在仍然存在一个典型的“**主路径修好了，旁路接口和缓存边界还没完全收口**”的问题。

如果只看 `runtime/tools.py` 与 `core/search.py` 主链路，v1.6 已接近可收敛状态。  
但如果把 dashboard 也视为正式功能面，那么当前版本还**不应该把 scope 能力视为完全闭合**。

**综合结论**:

- `tool/runtime` 主链路：基本稳定
- `dashboard + scope` 组合面：仍需一轮修复
- merge 判断：建议至少先修复 `R2-C1`，再决定是否将 dashboard 的 scope 支持视为 v1.6 完整交付
