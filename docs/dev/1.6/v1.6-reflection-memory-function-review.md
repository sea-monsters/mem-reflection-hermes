# v1.6 反思记忆功能审查与补全方案

**日期**: 2026-06-12  
**审查范围**: 会话微反思、全量反思、信息提取、精炼、工具清理、压缩拼接、数据库注入、supersedes 链维护、graph 维护  
**当前基线**: mem-reflection-hermes v1.6 最新实现  
**参照实现**: `D:\Codex_lib\code_reference\mem0`, `D:\Codex_lib\code_reference\hy-memory`, `D:\Codex_lib\code_reference\graphiti`

---

## 1. 总体判断

当前插件已经具备完整的基础闭环：

```text
pre_llm_call 微反思
  -> on_session_end 全量反思
  -> episode/raw_chunk 存储
  -> episode compaction
  -> curator stale/supersedes/similar/orphan-edge 维护
  -> MemoryStore SQLite/frontmatter/event ledger
  -> graph co-activation / decay / superseded / deleted 状态维护
```

这说明 v1.6 不是“反思功能未完成”，而是已经完成了可运行的基础设施层。真正欠缺集中在两个方向：

1. **记忆精炼质量不足**: 默认 `raw_chunk` 更像可召回存证，不是高质量事实/决策/偏好抽取。
2. **作用域与图谱语义没有贯穿全链路**: v1.6 已实现 `user_id` / `agent_id` / `run_id` filters，但反思写入、graph 扩展、supersedes 语义判断仍有不一致点。

因此，下一步不应推翻当前实现，而应在现有闭环上增加一层轻量、可降级、可验证的“精炼记忆管线”。

## 2. 当前已完成能力

### 2.1 微反思触发与写入

入口在 `runtime/hooks.py::_pre_llm_call`。当前行为：

- 显式记忆意图立即触发。
- 否则约每 3 turn 触发一次。
- 过滤带 `tool_calls` 的 assistant 消息。
- 按当前 reflection mode 调用 `_run_micro_reflection()`。
- embedding/local/hybrid 模式下走 `_run_embedding_micro_reflection()`。

完成度判断：**基础可用，偏保守**。适合抓显式“记住/更正/偏好”，不适合提炼隐含决策和复杂根因。

### 2.2 全量反思与 session-end pipeline

入口在 `runtime/hooks.py::_on_session_end`。当前顺序：

1. graph decay
2. full reflection
3. episode compaction
4. memory curator
5. checkpoint cleanup

同时支持 pending stage 记录与 session start 恢复。

完成度判断：**运行闭环完整**。主要欠缺不是调度，而是 full reflection 默认内容形态偏 raw。

### 2.3 信息提取与精炼

`reflection/runtime.py` 当前提供三类路径：

- `raw_chunk`: 3-turn 窗口直接保存 episode，零 LLM 成本。
- `embedding/local`: 启发式抽取显式记忆意图、纠正、偏好、过程型技能。
- `llm/hybrid`: 结构化 LLM 输出 memory/skill/conflict。

完成度判断：**模式齐全，但默认质量上限较低**。`raw_chunk` 可保留上下文，但不是抽象后的长期记忆。

### 2.4 工具清理与噪声过滤

当前已有多层防护：

- `_format_messages_for_reflection()` 跳过 `tool` role 和 `tool_calls` assistant 消息。
- `_is_noise_text()` / `_is_memorable_content()` 拒绝工具输出、JSON/system note、执行结果、代码块、路径噪声等。
- curator cold-store `build_cold_entry()` 会 refine body，测试覆盖了 tool noise stripping。

完成度判断：**基本合格**。但工具结果中“有价值的结果摘要”与“无价值日志”目前是一起被保守过滤，缺少工具结果摘要器。

### 2.5 压缩拼接

当前存在两个层次：

- reflection transcript 有最大字符裁剪。
- `_compact_episode_zone()` 按天聚类 episode，生成 `compacted` summary，并用 `supersedes` 指向原始 episode。

完成度判断：**结构存在，但无 LLM 时摘要质量弱**。fallback 是最长文本截断，不能保证表达真实会话结论。

### 2.6 数据库注入、事件、supersedes、graph

`MemoryStore.put/update/delete/delete_by_filters` 已负责：

- Markdown/frontmatter 写入。
- SQLite `memories` / `supersedes` / tags / entities 索引维护。
- `memory_events` append-only ledger。
- supersedes 目标存在性与环路校验。
- active list 默认排除被 supersede 的旧 memory。

graph 侧已具备：

- session-end decay。
- post-tool co-occurrence enrichment。
- memory write 后 ensure meta / record access。
- supersedes 时旧节点降权、标记 `superseded`、迁移旧边到新节点。
- delete 时标记 `deleted` 并衰减边。
- curator 清理 orphan edges。

完成度判断：**基础维护能力完成**。欠缺是 typed relation、scope-aware graph 与 semantic supersedes 判断。

## 3. 六个欠缺点

### G1. 默认 `raw_chunk` 是存证，不是精炼

当前默认路径能把会话切块写入 episode，但不会稳定抽取：

- 用户偏好
- 项目约定
- 设计决策
- 失败根因
- 操作禁令
- 后续待办

影响：长期召回时会检索到原文片段，agent 仍需要二次阅读和推理。

### G2. embedding/heuristic 提取能力偏窄

当前启发式主要覆盖显式记忆意图、纠正、偏好表达和部分 procedure。对多轮会话中逐步形成的隐含结论不敏感。

影响：false negative 偏高，尤其是开发协作场景里的“我们刚刚决定以后这样做”。

### G3. scoped filters 没有贯穿反思写入

v1.6 已支持 `user_id` / `agent_id` / `run_id`，但反思生成的新 memory 多数只写 `scope="user"`，没有从 ctx/session 自动继承 scope fields。

影响：hosted、多 agent、多 run 场景里，反思产生的记忆可能变成全局可见或混入错误范围。

### G4. graph 仍是 co-activation，不是 typed knowledge graph

当前 graph 是 Hebbian co-activation graph，边表示“共同使用/共同出现”，不是“实体 A 与实体 B 有某种事实关系”。

影响：适合召回扩展，不适合回答结构化事实、关系推理、冲突失效。

### G5. supersedes 判断偏结构，不够语义化

当前链路能维护 supersedes 表、防环、压缩长链、归档旧链，但“是否应替代”主要依赖 LLM 输出、correction marker 或相似度冲突。

影响：可能漏掉真实 stale，也可能把相似但并存的 scope-specific 事实误判为替代。

### G6. compaction fallback 只是代表片段，不是真摘要

无 LLM 时 compaction 选择最长正文并截断，不能保证保留关键结论。

影响：随着 episode 增多，压缩层可能保留了最啰嗦的片段，而非最重要的事实。

## 4. 参考实现启发

### 4.1 mem0: scope/filter/metadata/history 一体化

参考点：

- `mem0/memory/main.py::_build_filters_and_metadata()` 同时构造 storage metadata 和 query filters，并要求至少一个 `user_id` / `agent_id` / `run_id`。
- `Memory.add()` 使用 `infer=True` 时先按 filters 检索已有 memory，再 LLM 抽取，再 hash dedup，再 batch persist，再 batch history，再 batch entity linking。
- `update()` 保留已有 `user_id` / `agent_id` / `run_id`，并做 entity-store cleanup + relink。
- 文档明确 entity-scoped memory 的边界和 filter debug 方法。

可借鉴结论：

1. scope 不应散落在 handler 参数里，应由中心化 helper 同时产出 write metadata 和 query filters。
2. 反思写入前应先按当前 scope 检索已有 memory，作为抽取与冲突判断上下文。
3. history/event/entity 维护应批处理，减少 per-memory 副作用漂移。

### 4.2 hy-memory: L0/L1/L1.5/L2/L3 分层

参考点：

- `l0-recorder.ts` 原始记录层只负责干净捕获 user/assistant 消息，并替换被 context 注入污染的 user prompt。
- `l1-extractor.ts` 对消息先做质量门，再做 scene segmentation + memory extraction，输出 persona/episodic/instruction 类型。
- `l1-dedup.ts` 先用 vector/FTS 找候选，再让 LLM 对候选批量判定 store/update/merge，失败时降级为 store。
- `after-tool-call.ts` 和 `context-token-tracker.ts` 有 token snapshot、阈值触发、轻量估算、L3 压缩策略。

可借鉴结论：

1. raw capture 与 refined memory 应分层，不要让 raw_chunk 承担长期记忆职责。
2. 精炼应先做质量门，再 scene segmentation，再类型化 memory。
3. dedup/supersedes 应采用“召回候选 + 批量语义判定”的高效路径，而不是对全库扫描。
4. 压缩应有 token/accounting 指标，不只按条数阈值。

### 4.3 graphiti: episode/entity/edge/temporal graph

参考点：

- `extract_nodes_and_edges.py` 单次抽取 entity nodes 和 relationship facts，强调 fact 必须 self-contained。
- graphiti 的 episode ingestion 会把 episode、entity nodes、entity edges、episodic edges 一起落库。
- edge dedupe/resolution 会产生 resolved edges 和 invalidated edges。
- search filters 支持 `valid_at` / `invalid_at` 等 temporal 条件。
- saga/episode chain 用 `NEXT_EPISODE` / `HAS_EPISODE` 保存 episode 顺序和归属。

可借鉴结论：

1. co-activation graph 可以保留，但应新增轻量 typed fact graph，不应混用同一语义。
2. supersedes 可以借鉴 temporal invalidation：旧事实不只是“被替代”，还应记录何时失效、为什么失效、被哪个新事实 invalidated。
3. episode 与 refined facts 应建立来源边，便于审计和回放。

## 5. 补全实现方案

### 5.1 新增 `ReflectionScopeContext`

目标：解决 G3，并为其他补强提供统一上下文。

建议新增模块：`reflection/scope_context.py` 或复用 `core/scope.py` 扩展。

职责：

- 从 `ctx.scope_filters`、`ctx.user_id`、`ctx.agent_id`、`ctx.run_id`、hook kwargs 中提取 scope。
- 产出 `write_fields` 和 `query_filters`。
- 明确 local 单用户兼容模式：无 scope 时保持现状。
- 在 reflection、compaction、curator、graph side-effect 中统一使用。

最小落点：

- `_run_embedding_micro_reflection(..., scope_context=None)`
- `_run_embedding_reflection(..., scope_context=None)`
- `_run_raw_chunk_reflection(..., scope_context=None)`
- `_compact_episode_zone(..., filters=None)`
- `_on_session_end()` 和 `_pre_llm_call()` 负责创建并传入。

验证：

- 微反思写入带 `user_id` 的 frontmatter。
- 全量反思 raw_chunk 写入带 `run_id`。
- compaction 只 compact 当前 scope 的 episode。
- 无 scope 的旧测试保持不变。

### 5.2 新增 `refined_fact` 反思模式

目标：解决 G1/G2，同时避免全量 LLM 成本失控。

建议新增模式：

```yaml
reflection:
  mode: refined_fact
  refined_fact:
    max_new_messages: 24
    max_background_messages: 12
    max_memories_per_session: 8
    llm_enabled: true
    fallback: embedding
```

管线设计借鉴 hy-memory：

1. L0 raw capture: 保留当前 raw_chunk 或 episode 原文，作为审计层。
2. L1 quality gate: 使用现有 `_is_noise_text()` / `_is_memorable_content()`，新增针对工具日志、代码 diff、重复输出的规则。
3. L1 extraction: 输出类型化候选：
   - `preference`
   - `constraint`
   - `decision`
   - `root_cause`
   - `procedure`
   - `todo`
   - `project_fact`
4. L1.5 candidate recall: 按当前 scope 召回 top-k 相似 memories。
5. L1.6 semantic decision: 对候选批量判定 `store` / `skip` / `supersede` / `scope_split` / `merge`。
6. L2 persist: 写入 `MemoryStore.put()`，保留 source episode ids。

高效策略：

- 没有 LLM 时降级为当前 embedding heuristic。
- 只有有足够新消息或显式记忆意图时运行 LLM。
- 批量抽取、批量 dedup，避免每条 memory 一次 LLM。
- raw_chunk 仍保留，但标记为 `source=raw_chunk`、`confidence=low`，不要当成唯一长期记忆。

### 5.3 工具结果摘要器

目标：解决工具清理过度保守的问题。

当前做法是过滤 tool role 和 tool_calls，能避免污染，但会丢掉有价值事实。例如测试结果、错误信息、构建产物路径、最终命令结论。

建议新增 `reflection/tool_summarizer.py`：

- 输入：tool name、args、result/status/duration。
- 输出：`ToolObservation`：
  - `kind`: `test_result` / `build_result` / `file_change` / `error` / `artifact`
  - `summary`: 一句可记忆摘要
  - `evidence`: 短证据，不超过 N chars
  - `should_memorize`: bool
- 只把摘要送入 refined_fact，不送原始日志。

验证：

- pytest “184 passed” 可被摘要为验证事实。
- 大段 stdout 不进入 memory body。
- 失败命令保留错误类型和目标命令，不保留全日志。

### 5.4 typed fact graph 作为第二图层

目标：解决 G4，不破坏当前 co-activation graph。

建议保留当前 `GraphIndex`，新增轻量表：

```sql
entity_nodes(id, name, type, normalized_name, user_id, agent_id, run_id, created_at)
fact_edges(id, source_id, target_id, relation_type, fact, memory_id, episode_id,
           valid_from, valid_until, invalidated_by, confidence, user_id, agent_id, run_id)
episode_links(episode_id, memory_id, relation)
```

抽取策略借鉴 graphiti：

- 每个 refined fact 必须 self-contained。
- entity name 不允许完整句子、路径模板、无指代 pronoun。
- edge 只从 refined facts 生成，不从 raw tool logs 生成。
- relation_type 可先用受控枚举：
  - `PREFERS`
  - `REQUIRES`
  - `DECIDED`
  - `FOUND_CAUSE`
  - `USES`
  - `BLOCKED_BY`
  - `VALIDATED_BY`

高效策略：

- 第一阶段不引入外部图数据库，只用 SQLite。
- 仅对 refined_fact 生成 entity/edge。
- co-activation graph 继续服务 graph-expanded recall。
- typed fact graph 服务 explainable relation recall 和冲突判断。

### 5.5 semantic supersedes resolver

目标：解决 G5。

建议新增 `reflection/supersedes_resolver.py`：

输入：

- new candidate
- scope context
- top-k existing candidates
- temporal/context hints

输出：

```json
{
  "action": "store|skip|supersede|scope_split|merge",
  "target_ids": [],
  "reason": "...",
  "confidence": 0.0
}
```

规则分层：

1. 明确 correction marker + 高相似度：可自动 supersede。
2. scope 不同：默认 `scope_split`，不 supersede。
3. 时间条件冲突：写 `valid_until` 或 `invalidated_by`，不直接删除。
4. 低置信度：store as parallel 或 pending audit。
5. LLM 可用时，对 top-k 候选批量判定。

落库策略：

- `supersedes_reason` 必填。
- 对 typed fact edge 设置 `valid_until` / `invalidated_by`。
- memory event 记录 resolver decision。

### 5.6 token-aware compaction

目标：解决 G6。

当前 compaction 由 episode 条数触发。建议改为条数 + token 双阈值：

```yaml
compaction:
  threshold: 20
  token_threshold: 6000
  summary_mode: refined_fact
  preserve_recent: 5
```

摘要策略：

1. 有 LLM：按 scene/day/run 生成 structured summary。
2. 无 LLM：用 extractive ranker，不再选最长文本。
3. summary body 包含：
   - decisions
   - preferences
   - constraints
   - failures/fixes
   - validation evidence
4. summary frontmatter 记录：
   - `source_episode_ids`
   - `raw_count`
   - `token_before`
   - `token_after`

验证：

- 同一天多个 raw episode 生成一个 summary。
- summary supersedes 原始 episode。
- scope 不同的 episode 不被合并。
- fallback summary 不包含工具日志正文。

| `src/utils/sanitize.ts` | L0/L1 捕获前的文本清理、code block stripping、capture gate | 补充 `_is_noise_text()`，尤其是 prompt 注入、重复符号、工具残留判定 | reflection quality gate |
| `src/core/record/l1-extractor.ts` | L1 精炼抽取：quality gate、new/background messages、scene segmentation、typed memories、数量上限、metrics | `refined_fact` 模式最直接的蓝本；复制“新消息 + 背景消息 + 类型化输出 + 上限”的结构 | `reflection/refined_pipeline.py` |
| `src/core/prompts/l1-extraction.ts` | 场景切分与 memory 类型抽取 prompt | 借鉴 persona/episodic/instruction 类型组织方式，但替换为本插件需要的类型 | refined extraction schema/prompt |
| `src/core/record/l1-dedup.ts` | 批量冲突检测：先 vector recall，失败降级 FTS，最后 LLM 批量 judgment | semantic supersedes resolver 的高效实现蓝本；先找 top-k 再判定，避免全库扫描 | `reflection/supersedes_resolver.py` |
| `src/core/prompts/l1-dedup.ts` | 冲突判定 prompt 与 batch result schema | 借鉴 action 输出结构，把本插件 action 固定为 `store/skip/supersede/scope_split/merge` | resolver schema 和 tests |
| `src/core/record/l1-writer.ts` | L1 记忆落盘；保留 sessionKey/sessionId/scene/type/priority/source ids | 写入 frontmatter 时补 `source_episode_ids`、`memory_type`、`priority`、`scene_name` | `MemoryFrontmatter` 扩展或 metadata 字段 |
| `src/core/scene/scene-extractor.ts`、`scene-index.ts`、`scene-navigation.ts` | scene 抽取、索引与导航 | Memory Palace 已有 zone，可借鉴 scene 作为 zone 内的细粒度主题索引 | palace recall + refined scene metadata |
| `src/offload/context-token-tracker.ts` | tiktoken token snapshot、message token cache、metadata 不计入 token | 改造当前粗略 token 估算，支撑 token-aware compaction 的可靠触发 | compaction token accounting |
| `src/offload/hooks/after-tool-call.ts` | post-tool token snapshot、阈值触发、inline L3 compression、跳过 memory pipeline 自身会话 | 借鉴工具结果处理和压缩触发的“先轻量估算，再精确计算”策略 | tool summarizer、token-aware compaction |
| `src/offload/mmd-injector.ts` | active memory document 注入，等待 L1.5 settle，避免注入未稳定内容 | context injection 可借鉴“只注入 active refined summary，避免半成品记忆污染上下文” | `memory/context.py` refined block |
| `src/utils/pipeline-manager.ts`、`serial-queue.ts` | pipeline 串行化、任务隔离、失败降级 | 若 refined_fact 运行变重，可借鉴串行队列避免 session_end 并发写入和竞态 | reflection async/queue hardening |

hy-memory 的核心价值在于分层：L0 保真，L1 精炼，L1.5 去重，L2 汇总，L3 压缩。开发时应优先借鉴它的阶段边界和失败降级，而不是一次性把所有逻辑塞回 `_run_full_reflection()`。

#### 6.1.3 graphiti 可借鉴模块

| 参考模块 | 主要功能 | 对本插件的借鉴点 | 对应改造点 |
|---|---|---|---|
| `graphiti_core/graphiti.py::add_episode_bulk()` | 批量 episode ingestion；抽取 nodes/edges；dedupe；resolve；落库；创建 episodic edges | typed fact graph 的整体管线蓝本：episode -> entities -> facts -> resolved/invalidated edges | typed fact graph ingestion |

| `graphiti_core/utils/maintenance/node_operations.py` | entity node 抽取、embedding、相似节点搜索、dedupe/resolve | 借鉴 node resolve 思路，避免同一实体多种写法重复建 node | entity node normalizer/resolver |

| `graphiti_core/driver/operations/entity_edge_ops.py` | entity edge 保存、查询、去重、批量操作 | 借鉴 DAO 边界，不要把 typed edge 写在 runtime hook 里 | `core/fact_graph.py` |

#### 6.1.4 与六个欠缺点的对应关系

| 欠缺点 | 优先参考 | 建议复用的成熟边界 |
|---|---|---|
| G1 raw_chunk 不是精炼 | hy-memory L0/L1、mem0 infer add | L0 保真 + L1 类型化精炼 + batch persist |
| G2 heuristic 提取偏窄 | hy-memory `l1-extractor.ts`、graphiti extraction prompt | scene segmentation、typed memory schema、self-contained fact |
| G3 scope 未贯穿 | mem0 `_build_filters_and_metadata()`、entity-scoped docs | write metadata 与 query filters 同源生成 |
| G4 graph 非 typed KG | graphiti add_episode_bulk、extract_nodes_and_edges | episode/entity/fact edge 分层，co-activation 与 typed relation 分离 |
| G5 supersedes 不够语义化 | hy-memory `l1-dedup.ts`、graphiti edge invalidation | top-k recall + batch judgment + temporal invalidation |
| G6 compaction fallback 弱 | hy-memory token tracker/L3、graphiti episode chain | token-aware trigger、source episode trace、structured summary |

### 6.2 分阶段开发计划

### Phase A: Scope 全链路修复

优先级最高，风险低，收益直接。

任务：

- 新增 `ReflectionScopeContext`。
- 微反思/全量反思/raw_chunk 写入继承 scope。
- compaction/curator 使用 scope context。
- 增加 scoped reflection tests。

参考实现：

- 主要参考 `mem0/memory/main.py::_build_filters_and_metadata()` 的“写入 metadata 与查询 filters 同源生成”。
- 参考 mem0 entity-scoped docs 中对 `user_id` / `agent_id` / `run_id` 的用途边界说明。
- 避免照搬 mem0 “必须至少一个 scope id” 的硬约束；本插件为了 local 单用户兼容，应保留无 scope 的 local-global 模式。

验收：

- `srh_memory_search(filters={"user_id": "u1"})` 能找到反思写入的新 memory。
- `filters={"user_id": "u2"}` 找不到 u1 反思 memory。
- 无 scope 兼容旧行为。

### Phase B: refined_fact 模式

优先级高，功能收益最大。

任务：

- 新增 typed extraction schema。
- 新增 quality gate + candidate recall + batch resolver。
- 默认保留 raw_chunk，refined_fact 作为可选模式。

参考实现：

- 主要参考 `hy-memory/src/core/record/l1-extractor.ts` 的 L1 抽取阶段：quality gate、new/background messages、scene segmentation、max memories per session。
- 参考 `hy-memory/src/core/prompts/l1-extraction.ts` 的 prompt 组织方式，但类型替换为本插件需要的 `preference/constraint/decision/root_cause/procedure/todo/project_fact`。
- 参考 `mem0/memory/main.py::_add_to_vector_store()` 的 batch embedding、hash dedup、batch history 思路。
- 参考 graphiti `extract_nodes_and_edges.py` 的 self-contained fact 规则，确保 refined memory 离开原始会话也能理解。

验收：

- 能从多轮会话抽取 decision/root_cause/constraint。
- 相似旧记忆走 skip/supersede/merge，不重复写。
- LLM 不可用时降级 embedding，不阻断 session end。

### Phase C: 工具结果摘要器

优先级中高，直接改善开发场景记忆质量。

任务：

- 对 test/build/git/file 操作结果做短摘要。
- refined_fact 只消费摘要，不消费原始 tool log。

参考实现：

- 参考 `hy-memory/src/offload/hooks/after-tool-call.ts` 的 after-tool 事件处理、memory pipeline 自身会话跳过、token snapshot 和阈值触发。
- 参考 `hy-memory/src/utils/sanitize.ts` 的 capture/extract gate，将工具日志和可记忆验证事实分开。
- 参考 mem0 `_create_procedural_memory()` 的 `remove_code_blocks` 思路，避免把代码块当长期事实。

验收：

- 测试通过、构建失败、文件生成等事实可进入候选。
- 大段 stdout 不进入 memory body。

### Phase D: typed fact graph

优先级中，建议在 refined_fact 稳定后做。

任务：

- SQLite entity/fact edge 表。
- 从 refined facts 抽 entity/edge。
- search 增加 relation recall hint。

参考实现：

- 主要参考 graphiti `graphiti_core/graphiti.py::add_episode_bulk()` 的批量落库顺序：episodes、episodic edges、resolved nodes、resolved edges、invalidated edges。
- 参考 `graphiti_core/prompts/extract_nodes_and_edges.py` 的 entity/fact 抽取规则，特别是 entity 不能是完整句子、模板变量、泛词。
- 参考 `graphiti_core/utils/maintenance/node_operations.py` 的 node resolve 思路，避免实体重复。
- 参考 `graphiti_core/driver/operations/entity_edge_ops.py` 的 DAO 分层，把 typed graph 操作放进 `core/fact_graph.py`，不要散落在 hooks。

验收：

- 能按实体查关联 fact。
- 能从 memory 找 source episode。
- scope 不同的 entity/edge 不混合。

### Phase E: semantic supersedes 与 temporal invalidation

优先级中，依赖 refined_fact 和 typed graph。

任务：

- resolver 输出 action。
- event ledger 记录 decision。
- typed edges 支持 invalidated_by / valid_until。

参考实现：

- 主要参考 `hy-memory/src/core/record/l1-dedup.ts` 的“vector/FTS 召回候选 + LLM batch judgment + 失败降级 store”。

验收：

- correction 自动 supersede。
- scope_split 不误替代。
- history 能展示旧 fact 何时、为何失效。

### Phase F: token-aware compaction

优先级中，适合最后补强。

任务：

- token threshold。
- structured summary fallback。
- source episode ids 与 token accounting。

参考实现：

- 主要参考 `hy-memory/src/offload/context-token-tracker.ts` 的 token snapshot、message token cache、metadata 排除。
- 参考 `hy-memory/src/offload/hooks/after-tool-call.ts` 的 mild/aggressive/emergency 阈值和轻量估算优先策略。

## 8. 最终建议

v1.6 当前实现已经适合作为“可靠存储与基础反思闭环”。下一步最有效的路线不是继续扩大工具数量，而是把反思结果从 raw episode 提升为 typed refined memory。

建议采用以下原则：

- **raw_chunk 保留为审计层**，不要让它承担长期精炼记忆职责。
- **refined_fact 成为高质量长期记忆层**，负责 decision、preference、constraint、root cause、procedure。
- **scope context 成为所有反思写入和维护副作用的必经参数**。
- **co-activation graph 与 typed fact graph 分层**，避免把“共同出现”和“事实关系”混成一种边。
- **supersedes 从结构链升级为语义决策**，并用 event ledger 与 temporal invalidation 解释为什么替代。

按这个方案补全，可以在不推翻 v1.6 现有代码的前提下，把插件从“会存、会搜、会维护”推进到“会提炼、会归因、会隔离、会解释”。
