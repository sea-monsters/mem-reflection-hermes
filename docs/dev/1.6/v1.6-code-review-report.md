## CRITICAL (Block Merge)

### C1 — Schema blocks batch delete (`srh_memory_delete`)

**Location**: `runtime/schemas.py:39-47`, `runtime/tools.py:835-842`

**Problem**: `_SRH_MEMORY_DELETE_SCHEMA` declares `"required": ["id"]`, and its description says `"Requires id when specified."` (line 44). However, the implementation in `_tool_srh_memory_delete` (lines 260-268) supports `filters`-only batch delete:

```python
if not mem_id and not filters:
    return _jd({"error": "id or filters is required"})
if filters:
    count = mem_store.delete_by_filters(filters)
    return _jd({"success": True, "deleted_count": count})
```

When Hermes validates tool calls against the schema, it will reject any call that omits `id` — even when `filters` is provided. This makes the batch-delete feature **unreachable through the tool surface**.

**Fix**: Change `required` to conditional logic (schema-level `anyOf` or `oneOf`), or relax `required` to `[]` and validate in the handler.

---

### C2 — Schema definitions in `schemas.py` are orphaned / drifted

**Location**: `runtime/schemas.py` (all 12 schemas), `runtime/tools.py:register()` (lines 768-1020)

**Problem**: `register()` inlines its own schema dicts for every tool. It does **not** import from `runtime/schemas.py`. The `_SRH_MEMORY_*_SCHEMA` variables in `schemas.py` are defined but never referenced by the registration path. This creates a maintenance hazard: changes to `schemas.py` do not affect actual tool registration.

Additionally, the delete schema description at line 44 is misleading (see C1), and `schemas.py` lacks a schema for `srh_memory_history` entirely.

**Fix**: Either:
- (Preferred) Make `register()` import schemas from `schemas.py` and extend them with `handler`/`description`/`emoji`; OR
- Delete `schemas.py` entirely if it serves no purpose, and document that schemas live in `tools.py`.

## HIGH (Should Fix Before Merge)

### H1 — Search results omit scope fields

**Location**: `runtime/tools.py:145-159`

**Problem**: `_tool_srh_memory_search` builds the result item dict with `id`, `zone`, `confidence`, `pinned`, `tags`, `body`, `explain` — but **omits** `user_id`, `agent_id`, and `run_id`. A caller who filters by `user_id="alice"` cannot tell from the response which memories matched the filter.

**Fix**: Add the three scope fields to the item dict when they are non-None:

```python
for field in ("user_id", "agent_id", "run_id"):
    val = getattr(m.frontmatter, field, None)
    if val is not None:
        item[field] = val
```

---

### H2 — History events return raw JSON strings for frontmatter

**Location**: `runtime/tools.py:327-328` (via `get_memory_events` in `core/store.py:645`)

**Problem**: `get_memory_events` returns raw `sqlite3.Row` dicts where `old_frontmatter` and `new_frontmatter` are JSON strings. `_tool_srh_memory_history` forwards these raw rows without parsing. Consumers receive `"{\"id\":\"abc\"}"` instead of objects.

**Fix**: In `_tool_srh_memory_history`, parse the JSON strings before adding to the payload:

```python
import json
events_out = []
for e in payload["events"]:
    e_out = dict(e)
    for key in ("old_frontmatter", "new_frontmatter"):
        if e_out.get(key):
            try:
                e_out[key] = json.loads(e_out[key])
            except json.JSONDecodeError:
                pass  # keep raw string on parse failure
    events_out.append(e_out)
payload["events"] = events_out
```

### H3 — `MemoryStore.update()` does not support scope field mutation

**Location**: `core/store.py` (method signature not inspected in detail, but agent confirmed it lacks scope params)

**Problem**: Once a memory is written with `user_id="alice"`, there is no supported way to change it to `"bob"` via `update()`. The test `test_update_ignores_scope_field_changes` (line 246) asserts that scope is preserved, which is correct for v1.6 — but this should be **documented** because callers may expect `update()` to be a general-purpose mutation method.

**Fix**: Add a code comment on `update()` documenting that scope fields are immutable after creation. If future versions want to support scope migration, add explicit parameters with validation.

---

### H4 — Frontmatter truncation in events is silent

**Location**: `core/store.py:597-620`

**Problem**: `_record_memory_event` truncates frontmatter JSON to 8KB (line 617: if `len(result) > 8192`, replace with `{"id": data.get("id", "")}`). This data loss is **silent** — no warning is logged.

**Fix**: Add a `logger.warning` when truncation occurs:

```python
if len(result) > 8192:
    result = json.dumps({"id": data.get("id", "")}, ensure_ascii=False)
    logger.warning("Event frontmatter truncated for memory %s", data.get("id", "?"))
```

---

### H5 — Unknown filter keys are silently ignored

**Location**: `core/store.py:911-919`, `core/search.py:559`

**Problem**: `list()` iterates only over `("user_id", "agent_id", "run_id")`. If a caller passes `filters={"user_od": "alice"}` (typo), the misspelled key is silently ignored and the query returns unfiltered results. The same applies to `SearchIndex._search_impl` which passes `filters` verbatim to `store.list()`.

**Fix**: Add validation in `list()` to reject unknown keys:

```python
allowed_keys = {"user_id", "agent_id", "run_id"}
unknown = set(filters.keys()) - allowed_keys
if unknown:
    raise ValueError(f"Unknown filter keys: {unknown}")
```

## MEDIUM (Consider Fixing)

### M1 — `MemoryStore.search()` lacks `filters` in signature

**Location**: `core/store.py:1019`

**Problem**: `search()` signature is `search(query, k=5, include_history=False, zone=None)` — no `filters` param. `fusion_search()` at line 1022 has `**kwargs` which forwards to `SearchIndex.search()`, so `filters` works through `fusion_search` but not through the more obvious `search()` method. This is a **semantic trap**.

**Fix**: Add `filters: Optional[Dict[str, Optional[str]]] = None` to `search()` and forward it.

---

### M2 — `MemoryFrontmatter.new()` is not scope-aware

**Location**: `core/models.py:49-63`

**Problem**: The factory method `MemoryFrontmatter.new()` does not accept `user_id`/`agent_id`/`run_id` parameters. Callers must construct the frontmatter manually or set fields after creation.

**Fix**: Add optional scope params to `new()`:

```python
def new(cls, source, confidence="medium", tags=None, zone=None, pinned=False,
        user_id=None, agent_id=None, run_id=None):
    fm = cls(...)
    fm.user_id = user_id
    fm.agent_id = agent_id
    fm.run_id = run_id
    return fm
```

---

### M3 — Graph expansion ignores scope filters

**Location**: `runtime/tools.py:163-166`

**Problem**: After `_tool_srh_memory_search` gets filtered results, it calls `_get_graph_neighbors()` (line 163) with only `zone_filter`, not scope filters. Graph neighbors may include memories from different `user_id`/`agent_id`/`run_id`, leaking data across scope boundaries.

**Mitigation**: Graph neighbors are supplementary (they do not replace the primary results) and are capped at `max_results=k`. The risk is limited, but in a multi-tenant scenario this could leak memory references.

**Fix**: Apply scope filtering to graph-expanded results, or document that graph expansion is scope-agnostic.

---

### M4 — `list()` filter logic is duplicated in `delete_by_filters()`

**Location**: `core/store.py:911-919` vs `946-963`

**Problem**: Both methods build `clauses`/`params` from `filters` using identical loops. This duplication invites divergence during future maintenance.

**Fix**: Extract `_build_scope_clauses(filters)` helper returning `(clauses, params)`.

## LOW (Optional)

### L1 — Empty string scope values are persisted

**Location**: `core/models.py:77`

**Problem**: `to_dict()` writes `user_id=""` to frontmatter because the condition `v is not None` is true for empty strings. Empty string is semantically equivalent to `None` (no scope), but it will be stored and searched as `""`.

**Fix**: Normalize empty strings to `None` in `to_dict()` or `parse_frontmatter()`.

---

### L2 — `get_memory_events` Python API returns JSON strings

**Location**: `core/store.py:645-646`

**Problem**: The Python API returns raw sqlite3 rows where frontmatter fields are JSON strings. This is acceptable for the tool layer (which serializes to JSON anyway), but inconvenient for internal Python consumers.

**Fix**: (Optional) Add a `parse_frontmatter: bool = False` parameter to `get_memory_events` for convenience.

---

### L3 — No format validation on scope IDs

**Location**: `core/models.py`, `runtime/tools.py`

**Problem**: `user_id`, `agent_id`, `run_id` accept any string (including SQL-safe but semantically invalid values like `"' OR 1=1 --"`). While parameterized queries prevent injection, there is no length limit or format check.

**Mitigation**: SQLite VARCHAR has no practical length limit, but frontmatter YAML could become unwieldy. Consider a 255-char limit.

---

### L4 — `schemas.py` lacks `srh_memory_history` schema

**Location**: `runtime/schemas.py`

**Problem**: The 12th schema (`srh_memory_history`) is only defined inline in `runtime/tools.py::register()`. `schemas.py` has 11 of 12 schemas.

**Fix**: Add `_SRH_MEMORY_HISTORY_SCHEMA` to `schemas.py` (or resolve C2 by making `schemas.py` authoritative).

### Q1 — Schema duplication across `tools.py` and `schemas.py`

See **C2**. The duplication is a maintenance hazard.

### Q2 — `delete_by_filters` uses `SELECT *`

**Location**: `core/store.py:965`

**Problem**: `SELECT *` is brittle against future schema additions. `_row_to_loaded` may fail if a new column is added that it does not understand.

**Fix**: Use explicit column list: `SELECT id, scope, path, body, zone, ...`.

### Q3 — No centralized filter clause builder

See **M4**. Extract `_build_scope_clauses(filters)` to unify `list()` and `delete_by_filters()`.

## SECURITY

### S1 — Filter keys are concatenated into SQL

**Location**: `core/store.py:914-918`

**Problem**: `clauses.append(f"{key} = ?")` concatenates `key` directly into the SQL string. However, `key` is drawn from a hardcoded tuple `("user_id", "agent_id", "run_id")`, so injection is impossible in the current code. If this tuple is ever made dynamic (e.g., from user input), the risk becomes real.

**Mitigation**: Add a `ALLOWED_FILTER_KEYS` constant and assert membership before concatenation. This is defensive and documents the safety invariant.

**Current risk**: Negligible (hardcoded keys only).
