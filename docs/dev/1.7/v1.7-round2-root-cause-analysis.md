**日期**: 2026-06-13  
**范围**: mem-reflection-hermes v1.7（核心存储、检索、反射、运行时、仪表盘、curator）  
**方法**: git 历史追溯 + 全仓库模式扫描 + 设计文档/实现对比  
**依赖**: 第一轮报告 `docs/dev/1.7/v1.7-round1-systematic-debugging-review.md`

## 执行摘要

第二轮追溯确认了第一轮提出的四个跨领域主题，并定位到具体的架构债务根源：

1. **Dashboard graph 服务接入是包重构的遗留缺口**：commit `394729b` 将 `runtime_graph.py` 重命名为 `runtime/graph.py` 并新增 `graph/compat.py`，但 `web/api.py` 在同年同日创建时仍然引用旧路径 `..runtime_graph`。v1.6 的 follow-up audit（`810b7f7`）只把部分 `pass` 改为 `logger.warning`，没有修正根本的导入错误。
2. **静默失败是系统性的“防御式编程”过度**：全仓库有 80+ 处 `except Exception:`，其中约 25 处涉及数据持久化、核心 reflection、graph sidecar、bridge 等路径，却使用 `logger.debug` 或直接 `pass`。这与项目约定“降级功能用 `logger.warning`”冲突。
3. **Scope filter 语义在 `None` / `{}` / `{field: None}` 之间存在泄漏**：代码中混用这三种形态表示“全局”“要求 IS NULL”“无过滤”，导致 search、curator、dashboard 的边界行为不一致。
4. **Graph 能力通过内部属性 `store._graph` 传播**：typed fact sidecar、search Hebbian boost、bridge/cold-store 恢复等多处依赖该私有约定，没有统一的 graph-for-store 抽象。

## 关键发现详情

### 主题 1：Dashboard graph 服务接入的架构漂移

#### 历史追溯

- **commit `394729b`**（2026-06-08）“refactor: reorganize 11 flat modules into 5 functional packages”
  - 删除：`runtime_graph.py`
  - 新增：`runtime/graph.py`、`graph/compat.py`
  - 说明：`runtime_graph.py` 被整体迁移到 `runtime/graph.py`，`graph/compat.py` 作为向后兼容别名。
- **commit `810b7f7`**（2026-06-12）“v1.6: Systematic debugging follow-up audit”
  - 修改了 `web/api.py` 中 6 个 `pass` 为 `logger.warning`。
  - **未修改**：`web/api.py:130-146` 仍然导入 `..runtime_graph` 和 `mem_reflection_hermes.runtime_graph`。

#### 当前代码状态

```python
# web/api.py:130-146
def _get_graph_interface():
    try:
        from ..runtime_graph import GraphManagerCompat
        from ..store import plugin_data_dir
        return GraphManagerCompat(plugin_data_dir() / "graph.db")
    except ImportError:
        try:
            from mem_reflection_hermes.runtime_graph import GraphManagerCompat
            from mem_reflection_hermes.store import plugin_data_dir
            return GraphManagerCompat(plugin_data_dir() / "graph.db")
        except Exception:
            logger.warning("Graph init (runtime_graph) failed", exc_info=True)
            return None
    except Exception:
        logger.warning("Graph init failed", exc_info=True)
        return None
```

#### 根因分析

- `..runtime_graph` 和 `mem_reflection_hermes.runtime_graph` 在包模式下均不存在；唯一存在的是 `graph/compat.py`（模块名 `mem_reflection_hermes.graph`），它通过 `sys.modules[__name__] = _runtime_graph` 把自己替换为 `runtime.graph`。
- 因此 `web/api.py` 的第一分支 `from ..runtime_graph import GraphManagerCompat` 会 `ImportError`，进入第二分支；第二分支 `from mem_reflection_hermes.runtime_graph import GraphManagerCompat` 也会 `ImportError`；最终返回 `None`。
- 结果：仪表盘所有 graph 相关端点（`/graph`、`/graph/neighbors`、`/graph/zones`、`/query`）在真实 Hermes 生产环境中无法使用真实 graph，只能退化到基于文件 supersedes 的边。

#### 其他引用旧路径的位置

- `scripts/check_v092.py:30, 107`：测试脚本引用 `runtime_graph_surface`，这是旧 v0.9.2 兼容检查脚本，可能已过时。
- `tests/test_runtime_graph_aliases.py:19-24`：测试通过 `importlib` 直接加载 `runtime/graph.py` 并命名为 `_runtime_graph`，这是测试内部变量名，不影响生产。
- 结论：**唯一影响生产的是 `web/api.py:130-146`**。

#### 推荐根本修正

引入统一的 graph manager getter，例如：

```python
def _get_graph_interface():
    """Resolve graph manager through canonical runtime.graph path."""
    try:
        from ..runtime.graph import get_graph_manager_compat
        from ..core.store import plugin_data_dir
        return get_graph_manager_compat(plugin_data_dir() / "graph.db")
    except Exception:
        logger.warning("Graph manager resolution failed", exc_info=True)
        return None
```

并补充一个包模式集成测试，验证 `TestClient` 启动后 `_get_graph_interface()` 返回非 `None`。

### 主题 2：系统性静默失败

#### 全仓库 `except Exception:` 分布

使用 `grep "except Exception"` 扫描 `.py` 文件，共找到 **80+ 处**。其中与数据持久化或核心功能相关、但日志级别不足的位置包括：

| 文件 | 行 | 行为 | 当前日志 | 建议 |
|---|---|---|---|---|
| `web/api.py` | 141, 144, 340, 363, 383, 476, 480, 589, 720, 731, 739, 789, 799, 805, 827, 842, 853, 894 | 吞掉 graph/CLUQI/curator/cache/stats 失败 | 多为临时 logger 或 warning | 统一使用模块 logger；在响应中返回 `degraded` 标记 |
| `reflection/runtime.py` | 187, 283, 898, 1695, 1861, 2214, 2245 | typed sidecar、archive、raw chunk、compaction 失败 | `logger.debug` | 提升为 `logger.warning(..., exc_info=True)` |
| `runtime/hooks.py` | 91, 159, 166, 248, 260, 287, 310, 358, 380, 440, 506, 531, 533, 574, 693 | checkpoint、context、bridge、graph enrichment、neighbor 失败 | 多为 debug | 数据路径 warning，可忽略路径保留 debug |
| `memory/bridge.py` | 92, 146, 162, 166, 277, 301, 429, 571, 579, 625 | bridge Dir A/B 多步骤失败 | 混合 debug/warning | 统一按“数据同步失败”提升为 warning |
| `memory/curator/actions.py` | 133, 165, 209, 270, 277, 303, 403, 429, 435, 465, 534, 555, 573, 583 | curator 各阶段失败 | 多为 debug | 在 CuratorResult.errors 中记录并 warning |
| `core/store.py` | 595, 1098 | entity extraction、reranker 初始化失败 | `logger.debug` | 提升为 warning |

#### 根因分析

- 项目早期强调“fail-open”，因此大量核心路径被设计为“失败时不阻塞主流程”。
- 在 v1.6 follow-up audit 中，部分 `pass` 被改为 `logger.warning`，但仅针对显式列出的 P0/P1/P2 项（如 L5-05 web/api.py 6 sites、L5-10 core/search.py 5 sites）。未被列入清单的位置保持 `logger.debug` 或 `pass`。
- 这形成了一种“打地鼠”式修复文化：只有被审计点到的位置才会修复，导致同一代码库内日志/降级语义不统一。

#### 推荐根本修正

建立分级错误处理约定并全库扫描执行：

1. **CRITICAL 路径**（数据持久化、reflection 写入、graph sidecar、bridge 同步、curator 归档）：使用 `logger.warning(..., exc_info=True)`，必要时在响应中携带 `degraded: True`。
2. **INFO 路径**（资源清理、连接关闭、可选组件初始化失败）：保留 `logger.debug` 或 `logger.info`。
3. **UI 路径**（dashboard API）：任何非致命失败都应在 JSON 响应中加入 `degraded` 字段，说明哪些子系统不可用。

### 主题 3：Scope filter 语义泄漏

#### 三种形态的实际语义

| 形态 | 含义 | 出现位置 | 问题 |
|---|---|---|---|
| `filters=None` | 无过滤，返回全部 | `core/scope.py:normalize_scope_filters`、`memory/context.py` | 与 `{}` 的“global-only”混淆 |
| `filters={}` | global-only（要求 `user_id IS NULL AND agent_id IS NULL AND run_id IS NULL`） | `core/scope.py:build_scope_clauses`、`core/search.py:check_conflict` | 调用方常把“无过滤”错误传成 `{}` |
| `filters={"user_id": None}` | 语义等价于 `{}` | 理论上可能出现 | 与 `filters=None` 同样混淆 |

#### 当前代码中的不一致

- `web/api.py:91-97`：`_scope_filters` 把 `scope_from_values` 的结果传入 `normalize_scope_filters`，返回 `None` 或 normalized dict。这意味着当用户不提供任何 scope 参数时返回 `None`（全局）。
- `core/scope.py:74-88`：`build_scope_clauses` 对 `{}` 返回空 `clauses` 和空 `params`，即不添加任何 SQL 过滤。这与“global-only”语义不同，但调用方可能误解。
- `memory/context.py:163-181`：`_list_pinned_scoped`、`_list_active_scoped`、`_search_scoped` 对 `TypeError` 进行 fallback，先调用无参 `list_pinned()` 再在内存中过滤。这种 fallback 在 store 方法签名变化时会静默改变语义。

#### 根因分析

- Scope filter 是 v1.6 追加的横向功能，通过 `core/scope.py` 集中管理，但各子系统（store、search、context、curator、dashboard）的接入是逐步打补丁完成的。
- 没有统一的“scope intent”枚举：`UNSCOPED`（无过滤）、`GLOBAL_ONLY`（要求 NULL）、`TENANT`（具体值）。
- 测试多使用显式 dict（如 `{"user_id": "u1"}`），没有覆盖 `None` vs `{}` 的边界。

#### 推荐根本修正

在 `core/scope.py` 中引入显式语义：

```python
class ScopeIntent:
    UNSCOPED = "unscoped"      # 返回全部
    GLOBAL_ONLY = "global_only"  # 仅返回 IS NULL
    TENANT = "tenant"          # 按提供的字段过滤
```

并修改 `build_scope_clauses` 以接受 `UNSCOPED` 时返回空过滤、`GLOBAL_ONLY` 时生成 `IS NULL`、tenant 时生成等值过滤。所有调用方统一通过 `scope_from_context` / `scope_from_values` 获得 `ScopeIntent` 对象。

### 主题 4：Graph/Store 耦合与 typed fact sidecar 可达性

#### `store._graph` 属性约定的传播

使用 `grep "\._graph\b"` 扫描到以下位置依赖 `store._graph`：

| 文件 | 行 | 用法 |
|---|---|---|
| `core/search.py:302` | 构造函数接收 `graph` 参数 | SearchIndex._graph |
| `core/search.py:782-807` | Hebbian boost | `self._graph.spread()` |
| `core/store.py:413` | `self._graph = None` | MemoryStore 初始状态 |
| `core/store.py:1100` | `_get_search_index` 传 graph | 创建 SearchIndex 时绑定 |
| `core/store.py:1103-1108` | `set_graph()` | 运行时绑定 graph |
| `reflection/runtime.py:160` | `_record_typed_fact_sidecar` | `getattr(mem_store, "_graph", None)` |
| `tests/test_fusion_rerank.py` | 171, 189, 220 | 测试直接设置 `si._graph` |
| `tests/test_typed_fact_sidecar.py:138` | 测试 store._graph = graph | 测试手动绑定 |

#### 运行时绑定顺序

1. `runtime/state.py:_get_mem_store()` 创建 `MemoryStore()` 时 `_graph = None`。
2. `runtime/state.py:_get_graph_mgr()` 创建 `GraphManagerCompat`。
3. `runtime/registration.py:165-175` 在 `register()` 中调用 `_get_mem_store()` 和 `_get_graph_mgr()`，并通过 `ms._post_delete_callbacks.append(_on_memory_delete)` 注册删除回调。
4. **关键问题**：`MemoryStore.set_graph()` 在 `runtime/registration.py` 中**未被调用**。`_search_index._graph` 在 `_get_search_index()` 创建时由 `MemoryStore._get_search_index()` 传入 `self._graph`（此时为 `None`），因此 search 的 Hebbian boost 在 runtime 初始化后可能始终为 `None`。

#### 需要验证的假设

- 如果 `set_graph()` 从未被调用，那么 `SearchIndex._graph` 在 runtime 启动后一直为 `None`，导致 `_search_impl` 中的 Hebbian boost 分支被跳过。
- `_record_typed_fact_sidecar` 依赖 `mem_store._graph`；在 reflection 路径中，如果 store 未绑定 graph，typed fact sidecar 会被静默跳过。

#### 推荐根本修正

在 `runtime/registration.py` 的 register 流程中显式调用 `ms.set_graph(gm)`，确保 search 和 typed fact sidecar 都能访问 graph：

```python
ms = _get_mem_store()
gm = _get_graph_mgr()
if ms is not None and gm is not None:
    ms.set_graph(gm)
```

并引入 `_graph_for_store(store)` 辅助函数，供 reflection/bridge/curator 使用，避免直接读取 `store._graph`。

## 新增同类问题

### A1. `SearchIndex._ensure_embed_index()` 在 scoped 查询时仍构建全局索引

- **位置**: `core/search.py:331-360`
- **观察**: `_ensure_embed_index()` 调用 `self.store.list_active()` 不带 filters，构建全局 embedding 矩阵；scoped search 再通过 `allowed_ids` 在输出时 mask。
- **根因**: “scheme C” 设计（v1.6）选择用全局索引 + 运行时 mask 来支持 scope，避免为每个 scope 维护独立索引。
- **风险**: 多租户场景下，embedding 索引包含所有租户数据，虽然通过 mask 过滤，但存在潜在的信息泄漏风险（通过向量相似度侧信道）。
- **推荐**: 在文档中明确这是“scheme C”的 trade-off，或评估为高频 scope 建立 per-scope 索引的必要性。

### A2. `MemoryStore._get_search_index()` 创建 SearchIndex 时 graph 可能为 None

- **位置**: `core/store.py:1087-1101`
- **观察**: `_search_index = SearchIndex(self, graph=self._graph, reranker=reranker)`，此时 `self._graph` 通常为 `None`。
- **根因**: store 先于 graph 创建，没有 lazy rebind 机制。
- **推荐**: 在 `set_graph()` 中同步更新已创建的 `_search_index._graph`，并使其生效。当前代码已做（`self._search_index._graph = graph`），但问题在于 `set_graph()` 未被调用。

### A3. Curator `CleanOrphanEdges` 的 scope 跳过语义未报告

- **位置**: `memory/curator/actions.py:568-569`
- **观察**: 当 `ctx.filters` 非空且非 admin_global 时直接返回空结果。
- **根因**: 设计者假设 orphan cleanup 必须全局执行，但未将“跳过”语义纳入报告模型。
- **推荐**: 在 `CuratorResult` 中增加 `skipped_reason` 字段。

### A4. `web/api.py` 多处使用临时 `import logging` 获取 logger

- **位置**: `web/api.py:214, 340-341, 383, 476-477, 480, 589, 720, 731, 739, 789, 799, 805, 827, 842, 853, 894-897`
- **观察**: 模块顶部已有 `logger = logging.getLogger(__name__)`，但许多地方仍临时 `import logging` 并 `logging.getLogger(__name__).warning(...)`。
- **根因**: 早期 copy-paste 或快速补丁遗留。
- **推荐**: 统一使用模块级 `logger`。

### A5. `_tool_srh_palace_recall` 在 scoped 模式下不返回 graph_expanded

- **位置**: `runtime/tools.py:591-593`
- **观察**: `return json.dumps({"results": out} if filters else _enrich_with_graph(...))`。当 `filters` 存在时，即使 `_enrich_with_graph` 可安全过滤，也直接丢弃 graph 扩展。
- **根因**: v1.6 scope 设计选择“scope 激活时禁用 graph 扩展以避免跨 scope 泄漏”。
- **推荐**: 文档与代码一致即可，但应在响应中加入 `graph_expanded: []` 以保持 schema 稳定。

### A6. `scope_from_values` 过滤掉 `None` 值，导致无法表达 `IS NULL`

- **位置**: `core/scope.py:38-47`
- **观察**: `scope_from_values` 只返回非 None 的字段，因此调用方无法通过它构造 `{user_id: None}` 这样的 global-only filter。
- **根因**: 该函数设计为“从离散参数构造 tenant filter”，未考虑 global-only 场景。
- **推荐**: 新增 `global_scope_values()` 或让 `scope_from_values` 支持显式 `None` 语义。

## 设计层面的根因总结

1. **重构后未完成的接口迁移**：`runtime_graph.py` → `runtime/graph.py` 的迁移在 dashboard 留下旧路径引用，说明大规模重构后缺少“生产路径冒烟测试”。
2. **fail-open 哲学的过度应用**：大量核心路径使用 `logger.debug` 吞异常，导致系统“看起来正常”但子系统已降级。
3. **横向功能（scope）缺乏统一语义模型**：scope filter 作为 v1.6 追加功能，被各模块以不同方式解释，没有 central intent model。
4. **Graph 生命周期未显式管理**：graph manager 的创建与 store/search 的绑定发生在不同模块，缺少注册时的显式 wiring。

---

## 下一步建议

1. 在 `runtime/registration.py` 中确认并补全 `ms.set_graph(gm)` 调用。
2. 修复 `web/api.py:_get_graph_interface()` 使用 `runtime.graph.get_graph_manager_compat`。
3. 在 `core/scope.py` 中引入 `ScopeIntent` 枚举，统一 `None`/`{}`/`{field: None}` 语义。
4. 建立全库错误处理分级约定，并批量把数据路径的 `logger.debug` 提升为 `logger.warning`。
5. 补充生产路径集成测试：仪表盘真实 graph 解析、reflection typed sidecar 真实写入、scope filter 的 `None`/`{}` 边界。
