**日期**: 2026-06-11
**参考系统**: mem0 (v1.x), hy-memory (TypeScript), graphiti (v0.x)
**当前基线**: mem-reflection-hermes v1.5 — 511 tests passed, runtime imports/schema drift 已修复

## 1. 当前 v1.5 能力快照

mem-reflection-hermes v1.5 已实现：

- **本地 Markdown + SQLite 持久化**: `core/store.py` 记忆存储、frontmatter、zone 体系
- **混合检索**: `core/search.py` — BM25 + 可选 embedding + RRF/加权融合 + entity boost + recency/effectiveness/supersedes 因子 + 可选 reranker + MMR + explain 输出
- **联想图记忆**: `core/graph.py` — 共现边、传播激活、衰减、PageRank、跨 zone 分析
- **反射与策展**: `reflection/runtime.py` + `memory/curator/` — 全/微反射、技能候选、策展流水线
- **上下文组装**: `memory/context.py` — stable/dynamic 分离、分级压缩
- **宿主集成**: `runtime/` 包 — hooks, tools, schemas, registration, checkpoint, late-binding

**v1.5 已修复的运营阻塞项**:
- runtime 过时 import 路径 (`runtime_reflection` → `..reflection.runtime` 等)
- schema/handler 漂移 (`explain`, `supersedes_reason`, `compile_profile` mode 对齐)
- test suite 清理: 511 passed, implementation leak 基本消除

## 2. 与 mem0 的差距

mem0 核心路径围绕显式的 add/update/delete/search 语义、provider factory、history 表、scoped filters、metadata preservation。

### 2.1 优势（我们强于 mem0）

| 维度 | mem-reflection-hermes | mem0 |
|---|---|---|
| 本地可审计性 | Markdown frontmatter + SQLite 索引，易于修复 | 黑盒 vector store 依赖 |
| Agent 专用组织 | zone、pinned、context bundle、skills、session reflection 为一等公民 | 通用 memory，agent 语义弱 |
| 依赖基线 | BM25 + regex-first entity 提取，无需外部 vector 基础设施 | 需要 embedding provider |
| 版本谱系 | `supersedes` 在前端可见 | 仅 history table 记录 |

### 2.2 差距（mem0 有，我们没有）

| 差距 | mem0 实现位置 | 影响 |
|---|---|---|
| **无 durable event ledger** | `mem0/memory/storage.py` history 表 | `update()` 原地修改文件，无变更记录 |
| **无 scoped filters (`user_id`/`agent_id`/`run_id`)** | `mem0/memory/main.py` `_build_filters_and_metadata` | 不足以支撑 multi-agent、multi-run、hosted service |
| **无可插拔 vector store 抽象** | `mem0/vector_stores/base.py` + `factory.py` | 后端限于本地 SQLite + numpy array |
| **无独立 entity vector collection** | `mem0/memory/main.py` `_upsert_entity()` + `entity_store` | entity 仅有 boost，无独立 embedding/link |
| **导入/导出/迁移能力不足** | `mem0/client/main.py` export/summary API | 无 competing-tool import 路径 |

## 3. 与 hy-memory 的差距

hy-memory 设计为强分层: L0 conversation → L1 atom → L2 scenario → L3 persona，加上短期上下文 offload 到轻量 Mermaid/task-symbol artifacts。

### 3.1 优势（我们强于 hy-memory）

| 维度 | mem-reflection-hermes | hy-memory |
|---|---|---|
| stable/dynamic 上下文分离 | ContextBundle + 分级压缩 | 有但 offload 为主 |
| 本地可读性 | Markdown 文件 + dashboard | 需要 gateway/offload service |
| 部署简单性 | 单插件，无需额外服务 | 需要 L0→L3 pipeline + offload service |

### 3.2 差距（hy-memory 有，我们没有）

| 差距 | hy-memory 实现位置 | 影响 |
|---|---|---|
| **无证据分层 (L0→L1→L2→L3)** | `src/core/conversation/l0-recorder.ts` → `l1-extractor.ts` → `scene-extractor.ts` → `persona-generator.ts` | 记忆层次基于 zone，非严格来源链 |
| **无 provenance-preserving offload** | `src/offload/` (Mermaid, refs/, mmds/, result_ref) | 压缩长工具日志但不外化到可溯源 refs |
| **无 warm-up/idle-time 调度** | `src/utils/pipeline-manager.ts` | 无 staged extraction 和 persona trigger |
| **无 trace→pattern→skill 路径** | `src/offload/index.ts` `createSkillWithBackend` | skill 生成仅为 pending candidate，无结构化链路 |

## 4. 与 graphiti 的差距

Graphiti 是时序上下文图引擎: episodes 为来源、entities/facts 为类型化图节点/边、事实有 validity window、增量摄取、旧事实无效化而非删除。

### 4.1 优势（我们强于 graphiti）

| 维度 | mem-reflection-hermes | graphiti |
|---|---|---|
| 联想图行为 | 共现、传播激活、PageRank、衰减 | 主要做事实图，联想召回弱 |
| 版本谱系 | `supersedes`, `valid_from`, `valid_until`, `context_scope` | 有但不同模型 |
| 轻量化 | 本地 SQLite 插件，无需 Neo4j/FalkorDB | 需要图数据库 |

### 4.2 差距（graphiti 有，我们没有）

| 差距 | graphiti 实现位置 | 影响 |
|---|---|---|
| **非时序知识图** | `graphiti_core/edges.py` `EntityEdge` (typed, attributed) | 边仅表示"一起使用"，非实体-关系-实体 |
| **无预设/学习本体** | `graphiti_core/namespaces/nodes.py`, `entity_types_utils.py` | 无 entity/edge type ontology |
| **来源追踪弱** | `EpisodicNode`/`HasEpisodeEdge` | 记忆和边未一致追溯 episode、source span |
| **时序真值处理浅** | `resolve_edge_contradictions` (设置 `invalid_at`/`expired_at`) | `valid_until`/`supersedes` 存在但无自动无效化 pipeline |
| **图检索非核心** | graph 是核心查询基底 | 图检索为补充 |

## 5. 差距优先级矩阵

| 波次 | 功能 | 参考来源 | 依赖外部组件 | 架构风险 | 价值 |
|---|---|---|---|---|---|
| **W1** | Memory Event Ledger | mem0 history | 无 (SQLite) | 低 | 基础设施，解锁审计/导出/回滚 |
| **W2** | Scoped Filters (`user_id`/`agent_id`/`run_id`) | mem0 filters | 无 (SQLite) | 低 | multi-agent/hosted 部署必需 |
| W3 | Context Offload + Evidence Refs | hy-memory offload | 无 (本地文件) | 中 | 长工具日志场景显著收益 |
| W4 | Typed Temporal Fact Graph | graphiti | 无 (SQLite 扩展) | 高 | 架构决策，应作为独立 layer |
| P2 | Pluggable Vector Store | mem0 factory | 新依赖 (Qdrant/Chroma 等) | 中 | 仅在 remote/vector-store 需求真实时 |
| P2 | Entity Vector Collection | mem0 entity_store | embedding 基础设施 | 中 | 已有 entity boost，独立 collection 增量价值 |
| P2 | Import/Export/Onboarding | mem0 client | 无 | 低 | 运营功能，可延后 |

## 6. v1.6 建议 Sprint 范围

### 6.1 纳入 v1.6 Sprint: W1 + W2

**理由**:
1. 均为 **SQLite-native** — 无新外部依赖
2. Event ledger 是所有其他功能的基础设施（审计、导出、回滚、history UI）
3. Scoped filters 立即改善 multi-agent / hosted 部署能力
4. 边界清晰、可测试；无需架构重写

### 6.2 延后到后续 Sprint: W3 + W4

**理由**:
- W3 引入新的 storage 子系统 (`offload/`, `refs/`, `mmds/`)
- W4 是独立架构轨道（typed fact graph vs 现有 Hebbian graph），需要独立 SDD/Test/Code 周期
- 两者各自需要完整的 Spec → Test → Code 方法论

### 6.3 不纳入 v1.6: P2 项

**理由**:
- Pluggable vector store 需要真实 remote backend 需求才值得投入
- Entity vector collection 增量价值有限（已有 regex-first entity boost）
- Import/export 是运营功能，不影响核心记忆能力
