## 1. 发现的问题（按 ROI 排序）

### 🔴 P1-1：typed fact sidecar 的"失效链路"是 dead code

**设计意图（SDD Phase D）**: 保留 Hebbian co-activation graph，同时新增轻量 typed fact sidecar，对标 graphiti 的 invalidation edge，支持事实的**时序真值**——当新记忆 supersede 旧记忆时，旧记忆关联的 typed facts 应被标记 `invalidated_by`。

**实现现状**（`grep invalidate_typed_fact` 全仓库）:
- `core/graph.py:233` 定义了 `invalidate_typed_fact(fact_id, invalidated_by)`
- `core/graph.py:748` 的 `remove_memory()` 在删除时用 COALESCE 填充失效标记
- **唯一调用方是 `tests/test_typed_fact_sidecar.py:87`**，生产路径零调用

整个 supersede / compaction 链路（`reflection/runtime.py` 中 5 处 `_record_typed_fact_sidecar` 调用：`L810, L979, L1696, L1844, L2210`）**只写不失效**。

**根因**: `_record_typed_fact_sidecar`（`runtime.py:166`）的签名只有 `relation/kind/subject/object/target_memory_id/episode_id/...`，**没有"被替代的旧 memory id"入参**，所以它无从知道要失效哪些 facts。Phase D 的 sidecar 设计只完成了"写入半"，"失效半"是 dead code。

**功能后果**:
- `_compact_episode_zone()` 把 N 条 raw episode supersede 成一条 summary（`runtime.py:2203`），但旧 episode 的 typed facts 永远 `invalidated_by IS NULL`
- micro/full/embedding reflection 的 supersede 分支同样不失效旧 facts
- `typed_facts(include_invalidated=False)` 查询会一直返回已被语义替代的过时事实

**为何被测试盲区掩盖**: `test_typed_fact_sidecar.py` 只测了 sidecar 表的 CRUD（record/query/invalidate），**没有测 supersede 路径是否触发 invalidate**。`test_semantic_supersedes.py` 只断言 resolver 的返回值，不涉及 sidecar。

### 🔴 P1-2：semantic supersedes resolver 的 `merge` / `scope_split` 动作被静默丢弃

**设计意图（SDD Phase C）**: 把替代判断从"结构上有 supersedes 标记"推进到"语义上适合替代"，返回 5 种动作（`store/merge/supersede/scope_split/skip`）。

**实现现状**: `reflection/runtime.py` 中 4 处调用 `resolve_semantic_supersedes` 的模式完全一致——**只处理 `skip` 和 `supersede`，其余三种全部 fall through 到"普通存储"**：

```python
# runtime.py 四处一致的调用模式（L1452、L1806、L769、L942）
plan = resolve_semantic_supersedes(...)
if plan["action"] == "skip":
    continue              # 处理 skip
if plan["action"] == "supersede":
    supersedes = plan["target_ids"]   # 处理 supersede
# merge / scope_split / store → 全部 fall through 到普通 put()
```

**功能后果**:
- **`merge` 丢失**: resolver 判定"决策/政策/偏好类语义更新应 merge"（`supersedes_resolver.py:94,125`），但调用方不创建 merge 关联，新记忆被当全新事实存入，旧事实既不 supersede 也不失效 → 出现**重复 + 漂移**，且 sidecar 里同一个事实会有两条 valid 记录
- **`scope_split` 丢失**: resolver 在跨 scope 冲突时返回 `scope_split`（`supersedes_resolver.py:80`），调用方既不建关联边也不报警，跨 scope 的"应并存"事实被悄悄写入当前 scope

**为何被测试盲区掩盖**: `test_semantic_supersedes.py` 只断言 `assert plan["action"] == "merge"` / `== "scope_split"`，**没有断言 reflection 调用方对 merge/scope_split 的处理行为**。`test_full_reflection_strips_supersedes_without_replacement_intent` 只覆盖了 `store`（显式 supersedes 被剥离）这一种动作。

### 🟠 P2-1：`kind` 字段的类型偏差——抽取层有，持久层没有，sidecar 误用

**设计意图（SDD Phase B）**: 让反思结果从 raw chunk 提升为类型化提炼（fact/preference/decision/todo…），kind 作为类型标签贯穿全链路。

**实现现状**:
- `extract_refined_memory_candidates`（`extraction.py:155`）给每个候选打 `kind`（intent/decision/preference/policy/correction/todo/procedure）
- `MemoryFrontmatter`（`core/models.py:33`）**没有 `kind` 字段**，`to_dict()` / `serialize_frontmatter()` 都不写它 → 记忆落盘后 kind 信息丢失，召回时无法按 kind 过滤
- `_record_typed_fact_sidecar` 把 `kind=cand.get("kind", "fact")` 写进 sidecar，但：
  - **LLM 模式下 kind 永远是默认值 `fact`**：`_FULL_REFLECT_SYSTEM` prompt（`runtime.py:343`）和 `_build_reflect_schema()`（`runtime.py:563`）的 JSON schema 里**根本没有 `kind` 字段**，LLM 不会返回 kind
  - 只有 embedding 模式（走 `extract_refined_memory_candidates`）的 kind 是真实的

**功能后果**: sidecar 的 `kind` 分布在 LLM 模式下全部退化成 `"fact"`，Phase B 的类型化提炼在 LLM 路径上失效。Phase B 与 Phase D 之间的接缝没对齐。

### 🟡 P2-2 / P2-3：架构债（本轮已一并处理，见第 2.4 / 2.5 节）

- **P2-2 `engine.py` 死代码 + 三份重复 helper**: `ReflectionEngine` 类只在 test 中使用；`_is_memorable_content` / `_is_noise_text` 等在 extraction/engine/runtime 三处重复且实现不一致（CJK 权重处理不同）；`engine.py:29` 的 `from .runtime import _memory_tokens` 在包模式下会 ImportError，靠 `except ImportError` 兜底。
- **P2-3 scope `None`/`{}` 语义**: 第二轮主题 3 已识别但未修，`build_scope_clauses({})` 返回空过滤（=返回全部），与 global-only 预期相反；GLOBAL_ONLY（IS NULL）意图此前完全无法表达。

## 2. 修复记录（按 ROI 顺序逐项执行）

### 2.1 P1-1 修复：打通 typed fact sidecar 失效链路

**状态**: ✅ 已完成

**实际动作**:

1. `core/graph.py` 新增 `GraphIndex.invalidate_facts_for_memories(memory_ids, invalidated_by, valid_until=None)` —— 批量失效方法。失效语义严格限定为"以这些 memory 作为 `source_memory_id` 的事实"（即该 memory 自己产生的事实），**保留**只把这些 memory 作为 `target_memory_id` 引用的关系边（如 distill 的 membership/mention 边属于其它来源，不应被剪枝）。SQL 用 `WHERE source_memory_id IN (...) AND invalidated_by IS NULL` 保证幂等。
2. `runtime/graph.py` 的 `_GraphStoreShim` 增加 `invalidate_facts_for_memories` 转发，与已有 `invalidate_typed_fact` 对齐。
3. `reflection/runtime.py::_record_typed_fact_sidecar` 增加 `superseded_memory_ids: Optional[List[str]]` 入参；在写入新 fact + entity mentions 后，若提供了该参数，调用 `graph.invalidate_facts_for_memories(superseded_memory_ids, invalidated_by=fm.id)`。函数用 `getattr(graph, "invalidate_facts_for_memories", None)` 探测，对未升级的旧 graph 兼容。
4. 把所有带 supersede 的 sidecar 写入点（full LLM、micro LLM、embedding micro、compaction 共 4 处；raw_chunk 无 supersede 不需要）改为传入 `superseded_memory_ids`：
   - full LLM / micro LLM：`fm.supersedes` + merge 目标
   - embedding micro：`fm.supersedes` + merge 目标
   - compaction：`[m.id() for m in mems]`（被折叠的全部 raw episode）

**测试**（`tests/test_typed_fact_sidecar.py`，新增 2 个）:
- `test_invalidate_facts_for_memories_bulks_invalidates_owned_facts`：验证批量失效只动 source 拥有的事实、保留 target 引用边，且 `include_invalidated=False` 不再返回。
- `test_compaction_invalidates_superseded_episode_facts`：端到端——3 条 raw episode 各写一条 sidecar fact，跑 `_compact_episode_zone`，断言被折叠的 episode 的事实全部 `invalidated_by != NULL`、active 查询为空。

**验证**: `tests/test_typed_fact_sidecar.py` 6 passed（含 2 个新增）。

### 2.2 P1-2 修复：补全 merge / scope_split 动作处理

**状态**: ✅ 已完成

**实际动作**:

1. `reflection/runtime.py` 新增 `_record_semantic_relation_sidecar(mem_store, fm, *, action, target_ids, reason, confidence)` 辅助函数。仅处理 `merge` / `scope_split`（`store`/`supersede` 不写语义关系边——后者由 `fm.supersedes` 承载谱系）：
   - `merge` → 写一条 `relation="merges"`、`kind="semantic_merge"` 的 typed fact
   - `scope_split` → 写一条 `relation="scope_split_with"`、`kind="semantic_scope_split"` 的 typed fact
2. 在全部 4 个 reflection 路径接入：
   - **embedding full**：把 resolver 的 `plan["action"]`/`target_ids`/`reason` 通过 `memory_candidates` 的 `semantic_action`/`semantic_target_ids`/`semantic_reason` 字段透传到存储循环；存储成功后，merge 调用 `_record_typed_fact_sidecar(superseded_memory_ids=targets)` 失效合并目标事实 + `_record_semantic_relation_sidecar(action="merge")`；scope_split 只记关系边（不失效，因为跨 scope 不应互相替代）。
   - **embedding micro**：把 `plan` 提升为函数级变量（原来只在 `if conflict_mem` 块内）；merge 时把目标加入 `merge_supersede_ids` 一并传给 sidecar 失效；scope_split 记关系边。
   - **LLM full / LLM micro**：`plan` 已在循环中构造；存储后若 `plan["action"] in ("merge","scope_split")` 则记关系边；merge 目标加入 sidecar 失效列表。
3. 关键契约保留：`test_full_reflection_strips_supersedes_without_replacement_intent`（`store` 动作 → `fm.supersedes == []`）未被破坏——`store` 路径不触发任何新增逻辑。

**测试**（`tests/test_semantic_supersedes.py`，新增 4 个）:

### 2.4 P2-2 修复：消除 engine.py 坏 import 与重复 helper

**状态**: ✅ 已完成

**实际动作**:

1. **修复 `engine.py` 坏 import**（latent ImportError）：`reflection/engine.py` 的 `try` 分支原本有 `from .runtime import _memory_tokens as estimate_tokens`，但 `runtime.py` 根本不定义 `_memory_tokens`（它定义 `_estimate_tokens`）。该 import 在包模式下必然 `ImportError`，靠 `except ImportError` 兜底走 importlib spec 才不崩——"能跑是巧合不是设计"。同时 `estimate_tokens` 在 engine.py 中**从未被使用**（dead import）。删除 `try` 与 `except` 两处的 `estimate_tokens` 绑定。
2. **消除 runtime.py 的重复 helper**（CJK 一致性 bug）：`runtime.py` 本地定义的 `_is_noise_text` / `_text_similarity` / `_is_memorable_content` 与 `extraction.py` 的实现重复，且 `_is_memorable_content` **不算 CJK 权重**（用 `len(text) < 15`，而 extraction 用 `effective_len = len + cjk_chars`）→ 中文短句在 micro-reflection 与 compaction fallback 评分里走不同判定。删除 runtime.py 的三处本地定义，改为从 `extraction.py` re-export 单一 CJK-aware 实现：
   ```python
   from .extraction import (  # noqa: E402,F401
       _is_noise_text, _is_memorable_content, _text_similarity,
   )
   ```
   模块级名保持不变（`_is_noise_text`/`_text_similarity` 仍在 `__all__`），向后兼容。
3. `ReflectionEngine` 类（engine.py，~150 行）保留——它只在 `test_reflect.py`/`test_e2e.py` 用到，删除会破坏测试且无生产收益；它内部那份 `_is_memorable_content` 是测试专用的本地副本，与生产路径无关，不在本次合并范围。

### 2.5 P2-3 修复：引入 ScopeIntent 显式语义，让 GLOBAL_ONLY 可表达

**状态**: ✅ 已完成

**设计判断（关键）**: 调用点扫描显示**所有生产 caller 都用 `normalize_scope_filters(...) or None` 或 `scope_from_values(...)`**，二者都会剔除 `None` 值、永远不会产出 `{}`。因此 `{}`（global-only/IS NULL 意图）**当前根本无法表达**，`build_scope_clauses({})` 的"返回空过滤=全部"行为被全仓库 `if filters:` 真值门广泛依赖。所以**正确且不破坏现有行为的修法不是把 `{}` 重载成 global-only**，而是新增一个显式的 GLOBAL_ONLY 意图通道。

**实际动作**（`core/scope.py`，纯增量）:

1. 新增 `ScopeIntent(str, Enum)`：`UNSCOPED` / `TENANT` / `GLOBAL_ONLY`（`str` mixin 以便 JSON/audit 序列化）。
2. 新增 `global_only_scope()` 构造器：返回带私有 marker `_scope_intent = "global_only"` 的 dict。marker key 加下划线前缀，永不与真实 scope 列冲突，也不会被当列名拼进 SQL。
3. `normalize_scope_filters` / `scope_from_context` / `scope_cache_key` 全部识别并保留该 marker：
   - `normalize_scope_filters` 校验 unknown key 时把 `_scope_intent` 加入白名单；保留 marker。
   - `scope_from_context` 在显式 filters 带 marker 时**不再 `or None`** 折叠（否则空 dict + marker 会被误判为 None）。
   - `scope_cache_key` 把 marker 编进缓存键，使 GLOBAL_ONLY 与 UNSCOPED 不共享缓存。
4. `build_scope_clauses` 增加 GLOBAL_ONLY 分支：检测到 marker 时返回 `["user_id IS NULL", "agent_id IS NULL", "run_id IS NULL"]` + 空 params。
5. `memory_matches_scope` 增加 GLOBAL_ONLY 分支：仅当 memory 的全部三个 scope 字段都是 NULL 时返回 True（GLOBAL_ONLY 在内存过滤层同样生效，供 `filter_memories_by_scope` 使用）。
6. **`{}` 行为刻意保持不变**（仍 = 不加过滤）：因为 `if filters:` 真值门遍布全仓库，重载 `{}` 会引发大面积回归。GLOBAL_ONLY 必须通过 `global_only_scope()` 显式表达。

**测试**（`tests/test_scope_filters.py`，新增 `TestScopeIntent` 类共 10 个）:
- 枚举值、`global_only_scope()` 带 marker、`build_scope_clauses` 三态（GLOBAL_ONLY 发 IS NULL × 3、`{}` 仍空、TENANT 发等值）。
- `normalize_scope_filters` 保留 marker、`scope_cache_key` 区分 GLOBAL_ONLY 与 UNSCOPED。
- `memory_matches_scope` GLOBAL_ONLY 拒绝 tenant 行、`scope_from_context` 保留 marker。
- **端到端**：`test_list_with_global_only_returns_only_null_scope_rows`——store.list 路径用 `filters=global_only_scope()` 只返回 NULL scope 行。

**验证**: `tests/test_scope_filters.py` 34 passed（含 10 个新增）；`tests/test_store.py tests/test_search.py tests/test_context.py` 同步 90 passed，确认现有 None/tenant 行为零回归。

### 4.4 本轮复查新发现：A5 残尾（palace_recall 响应 schema 不稳定）

**现象**: 第二轮 A5 报告称"文档与代码一致即可"，但其根因建议"在响应中加入 `graph_expanded: []` 以保持 schema 稳定"未被执行。`runtime/tools.py::_tool_srh_palace_recall` 在 `filters` 激活时返回 `{"results": out}`，缺少 `graph_expanded` 键；而 `srh_memory_search` 同类路径始终带 `graph_expanded`（即便为空）。调用方必须按"键是否存在"分支，违反 schema 稳定性。

**根因分析**: 第二轮把 A5 定性为"低优先、文档对齐即可"，但漏看了"schema 稳定性"这一更深层的契约要求。这是一轮报告分类偏松导致的残尾，而非新的设计缺陷——条件表达式 `{"results": out} if filters else _enrich_with_graph(...)` 直接丢弃了键。

**修正动作**（本轮当场执行）:
1. `runtime/tools.py::_tool_srh_palace_recall`：filters 分支显式返回 `{"results": out, "graph_expanded": []}`，schema 与 unfiltered 路径一致。
2. `tests/test_palace_recall.py` 新增 `test_scoped_recall_emits_stable_graph_expanded_key`：断言 scoped 响应仍含 `graph_expanded: []` 键，且 `_enrich_with_graph` 在 scoped 路径不被调用。

**验证**: `test_palace_recall.py` 14 passed；全量 **638 passed**（修复前 637 → 638）。
